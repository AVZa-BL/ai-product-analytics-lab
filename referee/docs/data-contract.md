# Data contract

Generated from the loader by `python -m referee.data_contract`. Do not edit this file by hand: a test fails if it differs from the generated text.

A folder of three CSV files (UTF-8, a header row) describes an experiment, with an optional `manifest.json` that may hold `exported_at_utc`. Every timestamp is ISO 8601 in UTC (`2026-04-11T00:02:25Z`, `2026-04-11 00:02:25+00`). Every row of the chosen experiment is read; nothing is sampled. A file that breaks the contract is refused with every problem listed, each with its file and line.

## The files

### `experiment_assignments.csv`

| Column |  | Meaning |
| --- | --- | --- |
| `experiment_id` | required | which experiment the row belongs to; one folder may hold several |
| `player_id` | required | the unit that was randomised; one row for each player in the assignments and the outcomes files |
| `arm` | required | the arm's name as the spec spells it |
| `assigned_at_utc` | required | when the player was assigned, as a UTC instant |
| `arm_config_version` | required | the configuration of the arm at the assignment, a whole number of at least 0 |
| `first_seen_at_utc` | read if present | when the product first saw the player; when the column is there every row must hold a UTC instant, not after `assigned_at_utc` |

### `experiment_exposures.csv`

| Column |  | Meaning |
| --- | --- | --- |
| `experiment_id` | required | which experiment the row belongs to; one folder may hold several |
| `player_id` | required | the player; a player may have several rows |
| `exposed_at_utc` | required | when the player was exposed, as a UTC instant; a player may have several rows |
| `arm_config_version` | read if present | the configuration the player saw at that exposure; when the column is there every row must hold a whole number |

### `experiment_outcomes.csv`

| Column |  | Meaning |
| --- | --- | --- |
| `experiment_id` | required | which experiment the row belongs to; one folder may hold several |
| `player_id` | required | the unit that was randomised; one row for each player in the assignments and the outcomes files |
| `first_purchase_at_utc` | required | when the player first bought, as a UTC instant, or empty if they did not; keep the column even if nobody buys, because RES-012 reads it |
| `window_end_utc` | read if present | when the player's outcome window closes; when the column is there every row must hold a UTC instant. Without it the window is taken to be 7 days from the assignment |
| `sessions_7d` | read if present | a whole number of at least 0; the built-in metric of that name |
| `purchases_7d` | read if present | a whole number of at least 0; when it is there, `first_purchase_at_utc` must be present exactly when it is above 0 |
| `revenue_usd_7d` | read if present | a number of at least 0; the built-in metric of that name |

## Metrics

A spec names the metrics it wants read: the primary metric, the guardrails and, optionally, `secondary_metrics`. Each is read from one column of `experiment_outcomes.csv`: the one named by its `column`, else the one named like the metric. The column holds one number for each player. For a `binary` metric every value is 0 or 1; for a `continuous` metric every value is a finite number. An empty cell or a value that is not a number makes the column unreadable as a metric. Any column of the file that is not listed above can hold a metric, and the names `experiment_id`, `first_purchase_at_utc`, `player_id`, `window_end_utc` cannot be used as `column`.

### Metrics Referee knew by name

The columns `sessions_7d`, `purchases_7d`, `revenue_usd_7d`, and `purchased_7d`, keep the kind and family below, so a spec written for the lab's export still works. A spec may declare another `family` for them.

| Metric | Kind | Family | Value for a player |
| --- | --- | --- | --- |
| `sessions_7d` | continuous | count | the column `sessions_7d` |
| `purchases_7d` | continuous | count | the column `purchases_7d` |
| `revenue_usd_7d` | continuous | revenue_like | the column `revenue_usd_7d` |
| `purchased_7d` | binary | binary | 1 if `purchases_7d` is above 0, else 0 (a column named `purchased_7d` is read instead, if the file has one) |

### Family

A metric's `family` says what its values look like, and so which simulated error rates Referee may quote for it. It is declared in the spec, or defaults to `binary` for a binary metric, to the table above for a built-in one, and to `other` for any other metric. The monitor's ledger prints the family each metric was read as.

| Family | Values | Effect |
| --- | --- | --- |
| `revenue_like` | an amount most players leave at 0 and a few make large | RES-008 quotes its simulated error rates; RES-004 allows for the skew |
| `count` | a whole number of events per player | no simulated error rate is quoted |
| `binary` | 0 or 1 | no simulated error rate is quoted |
| `other` | anything else (the default for a continuous metric on a column of your own) | no simulated error rate is quoted |

### When a metric cannot be read

A results review refuses to run and lists the problem. The monitor (`--mode monitor`) refuses only when the primary metric cannot be read; for any other declared metric it lists the reason in its ledger and goes on.

| Reason | Meaning |
| --- | --- |
| `column_missing` | the column the metric names is not in the outcomes file |
| `column_not_numeric` | the column holds an empty cell, or a value that is not a finite number, in some row |
| `values_not_binary` | the metric is declared binary and the column holds a value other than 0 or 1 |
| `kind_mismatch` | a built-in metric is declared with another kind than it has |
| `kind_unsupported` | the metric is declared `ratio`, which needs the delta method; it is not built |

The monitor adds `window_not_matured` (every analysed player's outcome window is still open) and `no_estimate` (the data allow no estimate; the statistics' reason is given).

## A worked example

The metrics of `examples/custom-metrics/spec.yaml`:

```yaml
primary_metric:
  name: tutorial_completion
  kind: binary
  baseline: 0.4
  column: tutorial_done # the column of experiment_outcomes.csv that holds 0 or 1 for each player

guardrails:
  - name: session_minutes
    kind: continuous
    baseline: 30
    baseline_std: 10
    column: minutes_played
    harmful_direction: decrease
    tolerance_relative: 0.10

secondary_metrics:
  - {name: levels_cleared, kind: continuous, family: count}
```

and the first rows of `examples/custom-metrics/experiment_outcomes.csv`, which holds no built-in metric column:

```csv
experiment_id,player_id,tutorial_done,minutes_played,levels_cleared,first_purchase_at_utc
tutorial_test,player_0000,1,47.7,7,
tutorial_test,player_0001,0,34.9,6,
tutorial_test,player_0002,0,30.7,9,
tutorial_test,player_0003,0,20.0,5,
tutorial_test,player_0004,1,32.3,9,
```

Run it with `python -m referee review-results examples/custom-metrics/spec.yaml examples/custom-metrics --experiment-id tutorial_test --as-of 2026-03-20T00:00:00Z --mode monitor`.
