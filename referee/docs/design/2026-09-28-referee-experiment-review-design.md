## 1. Objective

Build **Referee**: a deterministic experiment reviewer that takes a structured description of an A/B/n test and returns findings with severity, evidence, and remediation — at design time (hypothesis, power, groups, procedure) and at readout time (method selection, p-values, confidence intervals, guardrails, verdict).

One-line pitch: **ruff for experiments.** Every warning is a named rule. Advice is generated from rules, not improvised.

Referee is advisory. It never ships, stops, or decides anything on its own; it produces a recommendation with the blocking rule IDs attached. This matches the repository's existing stance that the agent evaluation "does not authorize autonomous decisions".

## 2. Why this module, why now

- The lab currently holds **no randomized evidence**. All three diagnostics are observational; the hybrid scenario's matched-control analysis explicitly refuses to claim causality. A randomized module closes the largest capability gap in the portfolio.
- Experimentation (SRM, variance reduction, stopping rules, multiple comparisons) is the most deeply probed skill in senior product-analyst interview loops.
- The hybrid scenario already asks "does the subscription cannibalize store purchases?" and answers with matched controls. A randomized version of the same question, with a section on where the two answers diverge and why, is a stronger story than either alone.

## 4. Core design decision: rules first, narration second

**Findings engine (deterministic, the product).** Pure Python; every check is a rule with:

```python
@dataclass(frozen=True)
class Finding:
    rule_id: str          # e.g. "DES-003"
    severity: str         # "blocker" | "warning" | "info"
    title: str
    evidence: dict        # the numbers that triggered it
    why_it_matters: str
    remediation: str
    references: tuple[str, ...]
```

A review is a list of findings plus a verdict. Same spec in → same findings out. Fully unit-testable: each rule has a triggering and a non-triggering fixture.

**Narration layer (optional, later).** A language model may restate findings in plain language for a memo. It may only speak about findings the engine emitted; anything else is refused. Its evaluation set is dominated by refusal cases ("can we call it on day 3?", "arm C is significant in Germany, ship there?", "SRM is only 0.4%, fine, right?"). It is not part of milestones 1–4.

Rationale: improvised statistical advice is the version a reviewer will take apart; rule-derived advice is testable, reproducible, and consistent with the repository's evidence discipline.

## 6. Experiment spec schema (milestone 1 deliverable)

Representation: `@dataclass(frozen=True)` classes built by `ExperimentSpec.from_dict(...)`. Standard library only — no pydantic, no YAML in milestone 1 (YAML loading arrives in milestone 2 together with the CLI; see section 14 on dependencies).

```yaml
referee_spec_version: 1
id: hybrid_offer_page_2026_10            # slug: ^[a-z0-9_]+$
title: Subscription offer page variants
owner: analytics

hypothesis:
  null: "The offer page variant does not change 7-day subscription conversion."
  alternative: "Variant B increases 7-day subscription conversion."
  direction: increase                     # increase | decrease | two_sided

population:
  randomization_unit: player              # player | user | device | session | cluster
  analysis_unit: player                   # defaults to randomization_unit
  eligibility: "Players who open the offer page and are not subscribed at exposure."
  daily_eligible_units: 4200              # integer >= 1
  exposure_trigger: offer_page_view       # the event that marks first exposure

arms:
  - name: control
    allocation: 0.5
    is_control: true
  - name: variant_b
    allocation: 0.5

primary_metric:
  name: subscription_conversion_7d
  kind: binary                            # binary | continuous | ratio
  baseline: 0.032                         # rate (binary) | mean (continuous) | ratio value (ratio)
  baseline_std: null                      # required > 0 for continuous and ratio; must be null for binary
  governed_reference: docs/metrics/hybrid_subscription.md   # optional; rule HYP-002 warns if absent

guardrails:                               # may be empty; rule PRO-003 warns if empty
  - name: refund_rate_14d
    kind: binary
    baseline: 0.018
    harmful_direction: increase           # increase | decrease
    tolerance_relative: 0.10              # breach when worse than baseline × (1 ± tolerance)

design:
  mde_relative: 0.05                      # > 0
  alpha: 0.05                             # 0 < alpha < 1
  power: 0.80                             # 0 < power < 1
  sided: two_sided                        # two_sided | one_sided
  planned_duration_days: 14               # >= 1
  min_duration_days: 14                   # >= 1 and <= planned_duration_days
```

### 6.1 Validation rules (raise `SpecError`, a `ValueError` subclass)

Collect **all** violations, then raise once with every message listed — one round trip for the author, not ten.

- `referee_spec_version` must equal 1.
- Unknown keys at any level are errors (catches typos such as `mde_relativ`).
- `id` matches `^[a-z0-9_]+$`; `title` non-empty.
- `hypothesis.null` and `.alternative` non-empty; `direction` in the enum.
- `population.randomization_unit` in the enum; `analysis_unit` defaults to it when omitted; `daily_eligible_units` integer ≥ 1; `exposure_trigger` non-empty.
- `arms`: at least two; unique names, and names that a report writes differently (23.1); exactly one `is_control: true`; every allocation > 0; allocations sum to 1 within 1e-9.
- `primary_metric.kind` in the enum; `binary` ⇒ 0 < baseline < 1 and `baseline_std` is null; `continuous`/`ratio` ⇒ `baseline_std` > 0; `baseline` finite.
- `guardrails`: unique names, and names that a report writes differently (23.1); same metric rules as above; `harmful_direction` in the enum; `tolerance_relative` > 0.
- `design`: bounds as annotated; `min_duration_days ≤ planned_duration_days`.

**Separation of concerns:** validation asks "is the spec well-formed?"; review rules ask "is the experiment well-designed?". An `analysis_unit` different from the `randomization_unit` is *valid* (the schema accepts it) but *reviewable* (rule HYP-003 emits a warning). Keep those two layers apart.

## 8. Rule catalogue — seed list

IDs are stable; documentation lives in `docs/referee/rules.md`. Severity is the default; some rules escalate on thresholds.

**Hypothesis (HYP)**
- HYP-001 blocker — hypothesis not falsifiable (no null, no direction, or metric not measurable in the spec).
- HYP-002 warning — primary metric has no governed reference in `docs/metrics/`.
- HYP-003 warning — analysis unit differs from randomization unit (variance underestimated; use cluster-robust SE or aggregate to the randomization unit).
- HYP-004 warning — one-sided test requested; require pre-registered justification.
- HYP-005 warning — primary metric is a ratio of two unit-level quantities; delta method required.

**Design (DES)**
- DES-001 blocker — underpowered: required n exceeds achievable n at planned duration (states the achievable MDE instead).
- DES-002 warning — planned duration not a whole number of weeks (weekly seasonality).
- DES-003 warning — planned duration < 14 days (novelty / primacy effects unobservable).
- DES-004 info — unequal allocation; reports power loss vs equal split.
- DES-005 warning — more than two arms with no α adjustment declared; applies Bonferroni by default, recommends Dunnett.
- DES-006 warning — randomization unit is player/user in a product with social or multiplayer features (interference; consider cluster randomization or state the SUTVA assumption).
- DES-007 blocker — exposure trigger is (or can occur) after the treatment starts acting (post-treatment selection).
- DES-008 warning — no pre-period covariate declared; CUPED unavailable.

**Procedure (PRO)**
- PRO-001 blocker — no stopping rule; peeking without a sequential design is prohibited.
- PRO-002 warning — no SRM check cadence declared (recommend daily).
- PRO-003 warning — no guardrails declared.
- PRO-004 info — bucketing salt not declared; reuse of a previous salt correlates assignment across experiments.

**Results (RES)**
- RES-001 blocker — SRM: χ² p < 0.001 against registered allocation. Verdict becomes `invalid`.
- RES-002 blocker — achieved n below registered n.
- RES-003 blocker — observed duration shorter than registered `min_duration_days`.
- RES-004 blocker — guardrail breached beyond tolerance in the harmful direction.
- RES-005 warning — post-hoc power requested; refused, reports CI width instead.
- RES-006 warning — multiple arms or metrics without adjusted p-values.
- RES-007 warning — effect by exposure week is non-stationary (novelty or decay).
- RES-008 warning — heavy-tailed metric (kurtosis / top-1% share above threshold); bootstrap CI reported alongside t-test.
- RES-009 blocker — ratio metric analysed without delta method.
- RES-010 warning — segment result cited without pre-registration (subgroup fishing).
- RES-011 warning — sample ratio drifts over time even when the total passes.

## 9. Statistics (milestone 2 and 4)

Implementations live in `power.py` and `analysis.py`; every formula is validated in tests against a reference.

- **Two proportions**, per-arm n: `n = (z_{1-α/2}·√(2·p̄·q̄) + z_{1-β}·√(p₁q₁ + p₂q₂))² / (p₂ − p₁)²`. Reference: `statsmodels.stats.power.NormalIndPower` with `proportion_effectsize`.
- **Two means**, per-arm n: `n = 2·σ²·(z_{1-α/2} + z_{1-β})² / δ²`. Reference: `statsmodels.stats.power.TTestIndPower`.
- **Multi-arm**: Bonferroni `α/(k−1)` as the default; Dunnett noted as the less conservative option.
- **Duration**: `ceil(n_total / daily_eligible_units)` rounded up to whole weeks.
- **SRM**: χ² goodness-of-fit of observed arm counts vs registered allocation; flag at p < 0.001 (the threshold used in the Kohavi–Tang–Xu treatment of SRM).
- **Ratio metrics**: delta method, `Var(Y/X) ≈ (1/μ_X²)·[σ_Y² − 2·(μ_Y/μ_X)·σ_XY + (μ_Y/μ_X)²·σ_X²] / n`. Reference: bootstrap on the same fixture.
- **CUPED**: `θ = cov(Y, X_pre) / var(X_pre)`, `Y_adj = Y − θ·(X_pre − mean(X_pre))`. Reference: variance reduction on a fixture with known correlation.
- **Heavy tails**: percentile bootstrap CI (seeded) reported next to Welch t.
- **Multiple comparisons**: Bonferroni and Benjamini–Hochberg; Dunnett if `statsmodels` exposes it in the pinned version, otherwise documented as out of scope.

References: Kohavi, Tang, Xu, *Trustworthy Online Controlled Experiments* (2020); Deng, Xu, Kohavi, Walker, *Improving the Sensitivity of Online Controlled Experiments by Utilizing Pre-Experiment Data* (CUPED, WSDM 2013); Deng, Knoblich, Lu, *Applying the Delta Method in Metric Analytics* (2018, arXiv:1803.06336); Fabijan et al., *Diagnosing Sample Ratio Mismatch in Online Controlled Experiments* (KDD 2019); statsmodels power documentation.

## 11. Guardrails ("360" requirements)

- No verdict without a pre-registered spec; the results review recomputes the spec hash and refuses on mismatch.
- Refuse a verdict when achieved n < registered n or duration < registered minimum (RES-002, RES-003).
- Never auto-decide: output is a recommendation with reasons and blocking rule IDs.
- Specs carry no personal data by construction (metric names, rates, counts only).
- Deterministic outputs (seeded bootstrap) so CI can diff JSON reports.
- Provenance on every report: spec hash, data hash, git SHA, package versions — same fields the existing diagnostics publish.
- Narration layer, when added, is restricted to emitted findings and evaluated mainly on refusals.
- Keep raw evidence immutable; repairs happen downstream, as in the three existing scenarios.

## 12. Testing strategy

- Every rule: one triggering fixture, one non-triggering fixture.
- Power functions: agreement with `statsmodels` within 1 unit of n across a grid of baselines, MDEs, α, power.
- Delta method: agreement with a seeded bootstrap within tolerance.
- CUPED: variance reduction on a fixture with known ρ equals `1 − ρ²` within tolerance.
- SRM: known χ² fixtures.
- CLI: golden-file tests for `review-design` and `review-results` JSON output.
- Determinism: same inputs → byte-identical report.

### 16.3 Validation rules settled during milestone 1

## 17. Amendment 2: milestone 2 decisions (2026-09-30)

Decided before milestone 2 was built. Sections 0 to 16 are left as written; where they disagree with this section, this section wins. "Delivered in" names the pull request that implements a decision: 2a (power), 2b (finding model and rules), 2c (YAML loader, CLI, rule documentation).

### 17.1 Power references (corrects sections 9 and 12)

The formulas in section 9 stand. The references named for them do not agree with them, so the tests use other statsmodels functions. Agreement was measured over grids of baselines, effect sizes, alpha, power, sidedness and unequal allocations.

| Quantity | Reference named in sections 9 and 12 | Measured agreement | Reference used instead |
| --- | --- | --- | --- |
| Two proportions | `NormalIndPower` with `proportion_effectsize` (an arcsine approximation) | 53 of 180 cases within 1 unit; worst gap 1,433 | `samplesize_proportions_2indep_onetail` with `alpha / 2` for a two-sided test: exact in every case |
| Two means | `TTestIndPower` (t-based) | 66 of 96 cases within 1 unit; worst gap 39 | `NormalIndPower` with `alternative="larger"` and `alpha / 2`: exact in every case |

Two conventions the tests must pin: in `samplesize_proportions_2indep_onetail` the returned size belongs to the first group, which is `prop2 + diff` (the treatment), and `ratio` is the second group's size over the first's; and a two-sided `NormalIndPower` call also counts the opposite tail, which the section 9 formula ignores. Delivered in: 2a.

### 17.2 Spec extension

Milestone 2's rules need facts the version-1 schema does not carry. Seven optional fields are added. A spec that is valid today stays valid, and an absent field is what makes the matching rule fire.

| Field | Values | Rule and when it fires |
| --- | --- | --- |
| `design.alpha_adjustment` | `none`, `bonferroni`, `dunnett` | DES-005: more than two arms and the field absent or `none` |
| `design.pre_period_covariate` | metric name | DES-008: absent |

## 18. Amendment 3: milestone 2c decisions (2026-10-02)

Milestone 2c delivers the loader, the report and the `review-design` command. These are the decisions it made that sections 0 to 17 do not record.

### 18.1 The spec's fingerprint

- `ExperimentSpec.sha256()` is the SHA-256 of `canonical_json()` encoded as UTF-8. The canonical JSON has sorted keys, no spaces, non-ASCII written as it is, and refuses NaN. It is built from `to_dict()`, which is schema-ordered and omits whatever was not given.
- The fingerprint covers the parsed spec, not the file's bytes. Comments, key order, flow or block style and number spelling (`4` against `4.0`) do not change it. Any change to a value does, and so does the order of `arms`.
- An absent optional field and an explicit `null` have the same fingerprint, and an empty `procedure` section is dropped, so adding an optional field in a later schema version does not change the fingerprint of an existing spec.
- Text is hashed as written, without Unicode normalisation. `shasum` on the YAML file will not reproduce the fingerprint; a `source_sha256` of the file's bytes was considered for the report and left out.
- The design's section 6 example has the fingerprint `b0332774feccd582db109bfffff10e1330ce418ab28471ccb625fe0b00af10e8`. A test pins it, so the canonical form cannot change unnoticed.

### 18.2 Loading YAML

The loader reads with `SafeLoader` and refuses, with a message naming the file, line and column, what PyYAML would resolve silently: a repeated key (it keeps the last), an unquoted `null:` key and other keys YAML reads as booleans or numbers, aliases and merge keys, and more than one document. A missing, unreadable or non-UTF-8 file is a `LoadError` naming the path. A mapping that is not a valid spec raises the spec's own `SpecError`.

One consequence of PyYAML implementing YAML 1.1: a number such as `5e-2` or `1e-2` is read as text, because a float needs a dot. It is reported by spec validation as a non-number; `0.05` or `5.0e-2` works.

### 18.3 Report and command line

- `python -m referee review-design <spec.yaml> [--format text|json]`. Exit status: 0 no blocker found, 1 at least one blocker, 2 the spec cannot be read or is not valid (and usage errors), 3 a failure inside Referee. Status 3 is added to section 17.4's three, because an uncaught Python exception exits with 1, which a pipeline would read as a blocker.
- Results go to stdout. Errors go to stderr as plain text with nothing on stdout, also under `--format json`.
- The report is one dict with a fixed key order and a `report_version` of 1: Referee version, the spec's id, title and fingerprint, the recommendation, the blocking rule IDs, counts by severity, and the findings. The JSON and the text are both made from that dict. It holds no timestamp, host or path, so the same spec reviewed by the same Referee gives the same bytes.
- The report does not carry the power plan itself; DES-001's evidence states the numbers that matter.

### 18.4 Rule documentation

- Every rule has a `fires_when` sentence beside its title, why-it-matters and remediation. `docs/rules.md` is generated from the rule code by `python -m referee.rules.docs`, and a test fails if the committed file differs. This replaces the file's planned location `docs/referee/rules.md` in section 3, in line with section 16.1.
- The page documents the rule definitions. No test can prove that a `fires_when` sentence describes its check function; the trigger and non-trigger tests of each rule are what pin the behaviour.
- A rule whose ID prefix has no group in the generator is refused, so the results rules (`RES`) cannot be added without deciding how they are documented.

### 18.5 Examples and the spec template

- Section 16.2 moved `docs/referee/spec-template.yaml` to milestone 2. It is replaced by two examples in `referee/examples/`: `offer-page-underpowered.yaml` (the section 6 example, which gets `revise` with blockers DES-001 and PRO-001) and `offer-page-powered.yaml` (the same experiment planned for 98 days with every optional field declared, which gets `proceed`). The second serves as the template: it is commented and every optional field is present.
- Each example's text output is stored in `referee/tests/golden/` and compared by a test, as is the JSON output of the powered example.

Delivered in: 2c.

### 20.4 Three results rules

- RES-007, which section 8 already lists, is the effect over time. It is defined as a test of whether an arm's difference against control differs between cohorts of players grouped by the week of their first exposure (Cochran's Q across the cohorts, with the slope per week reported next to it), not as a check that the last week is negative. ### 21.1 Evidence, and its limits

- The simulations were written for the purpose, and each was checked against `referee/src/referee/methods.py`: the vectorised statistics matched `welch_difference` and `cohort_heterogeneity` to within a relative 2e-12 on several hundred explicit cases. - (re-run) One small cohort kept next to two of 300 players per arm, normal data, 20,000 runs per row, seed 20261201 (Monte Carlo error 0.15 points at the 5% level, 0.07 at 1%): Cochran's Q flags 7.22% and 2.14% (nominal 5% and 1%) at 6 players per arm, 6.39% and 1.60% at 10, 5.55% and 1.32% at 20, 5.54% and 1.19% at 30, 5.11% and 1.08% at 50. - (re-run) Thirty players per arm in every cohort, 6,000 runs per row, seed 20261202 (error 0.28 and 0.13 points): Q flags 5.92% and 1.33% with 3 cohorts, 6.73% and 1.58% with 8, 6.75% and 2.00% with 12, 7.27% and 1.60% with 26. With each cohort's standard error multiplied by √(ν/(ν−2)), ν being the Welch degrees of freedom, the rates are 5.47% and 1.23%, 5.47% and 1.13%, 5.55% and 1.57%, 5.52% and 1.12%. The 12-cohort cell at 1% reads high in the same sample in which its uncorrected rate does; the studies' 100,000-run rows read 1.0% to 1.2% (reported). The cause is that the weights of Q are estimated from small samples. The correction is the studies' proposal, validated by simulation only; the author knows of no published source for it.

For a linear fade of the size the slope test detects with 80% power, Q detects it with probability 70.9%, 64.5%, 55.5%, 49.3% and 40.9% for 3, 4, 6, 8 and 12 cohorts (noncentral chi-squared; the slope test two-sided at 5% and Q at 5%, not the trigger of 21.5, which is stricter; 4b-2 gives its own figures at the levels it fixes and pins them in its own test).

The sample-ratio rules (RES-001, RES-011) use every assigned player at or after `design.start_utc` (every assigned player when the spec registers none; 21.8), exposed or not, so that dropping players from the analysis by exposure cannot hide a mismatch. `design.start_utc` is the one exception to "every assigned player": a start registered after the real launch leaves the earlier players out of every count, and the review carries their number (`ResultsReview.ignored_before_start`) so that this is visible. The effect rules (RES-004, RES-007, RES-008) use the players the lab's own analysis uses: assigned, exposed, and not first exposed after their first purchase. The analysed population has no bound on the delay between assignment and first exposure: a player first exposed late in, or after, their own seven-day window is analysed (the committed export has none).

A results review is refused, with every problem listed, and no rule runs, when the export has an arm the spec does not list; when a metric of the spec is not in the registry or has another kind there; when no player was assigned at or after `design.start_utc`; or when an assigned player has no outcome row.

### 21.4 Data-fit rules (4b-1)

- RES-001 (blocker): the sample-ratio check of section 9 on every assigned player, χ² p below 0.001 against the registered allocation (the exact multinomial test where an expected count is below 100; see Small counts below). The evidence carries the same check for each 7-day week of assignment, and which test each used.
- RES-002 (blocker): in the effect analysis, an arm has fewer players than that arm's required n from `plan_power(spec)`, found by arm name. A design that cannot be sized at all is reported as the design review does (DES-001), with the reason.
- RES-003 (blocker): the observed duration, first to last assignment in whole days rounded up, is shorter than `min_duration_days`. It spans every assigned player at or after `design.start_utc`, exposed or not. Rows before `design.start_utc` (21.8) are left out and listed, in the finding and in the report. Without `design.start_utc` one mistimed row (a timestamp of zero) sets the duration, so the finding's remediation asks for it.
- RES-011 (warning): the total passes but a week of assignment fails, each week tested at 0.001 divided by the number of weeks that hold assigned players. On the committed export the three weeks give p = 0.34, 4.0e-5 and 2.6e-8 (re-run); the total fails there (p = 6.7e-10), so RES-001 fires and RES-011 does not.
- RES-012 (warning): players first exposed after their first purchase; the count, their share of assigned players and of purchasers, and the estimate with and without them. It becomes a blocker when the late share of the exposed players differs between arms (χ² test of homogeneity across the arms, or the exact test where an expected count is below 100, p below 0.001); never-exposed players cannot be late and are not in that share. The estimate is the primary metric's difference per non-control arm against control with its unadjusted 95% interval, over all exposed players and over the analysed ones. No published threshold is known to the author, so this is a judgement. On the committed export 198 players (7.0%) are late-exposed, 7.1%, 7.4% and 6.4% by arm (homogeneity p = 0.72), so it stays a warning there (re-run).
- Small counts (RES-001, RES-011, RES-012). Pearson's χ² is an approximation, and at the tails these rules use it is too generous when an expected count is small. Measured in exact arithmetic, without simulation (re-run): for two arms, 5 expected units in the smaller arm, the χ² sample-ratio test at 0.00025 (a week of four) flags 4.0 times as often as its level at a 10% allocation and 5.9 times at 5%, and at 0.001 3.2 times at 10%; from 100 expected units on it stays within 0.85 to 1.23 times its level. For RES-012, with 950 and 50 exposed players sharing one late rate of 0.3%, χ² at 0.001 flags 14 times as often as its level (29 times with 990 and 10), and Fisher's exact test at most 0.65 times in every cell computed; arms of equal size are not affected (the χ² flags 0.00 times its level with 2,500 and 2,500). So where the smallest expected count (of units in an arm for the sample ratio; of late or not-late players in a group for homogeneity) is below 100, the rules use the exact test: the multinomial test of the counts against the allocation, and the exact conditional test of the 2 × k table (Fisher's for two arms, Freeman and Halton's for more). Both list every outcome (up to 1,000,000) and add up those no likelier than the one seen, as scipy's `binomtest` and `fisher_exact` do; beyond that the χ² is kept and the evidence says `method: chi_square`. The evidence of every such test carries its `method`; RES-012's also the smallest expected count. Checked against scipy's two tests to 1e-9 and against adding up every outcome by hand for three or more groups. An exact test is conservative: it never flags more often than its level, so a real mismatch among a few players may need a few more players to be flagged. What a stricter small-count rule would also cost: 8 late players in an arm of 1,000 against none among 9,000 still escalates (exact p = 1e-8), 2 do not (p = 0.010).
- RES-013 (warning): an arm's configuration version changes during the test; the versions by cohort week, the version at first exposure, and, where one week holds both, the difference between them. On the committed export 445 `variant_b` players are on version 2 and 11 have a first-exposure version that differs from the assigned one, counting every assigned player (re-run). The rule counts the analysed players only, so its finding shows 429 `variant_b` players on version 2 and none that differ, because all 11 are late-exposed (re-run).
- What the rules do not do. RES-012 and RES-013 read the analysed players only, so a player excluded as late-exposed counts toward no version change. RES-013 compares each later version in a week with the earliest version in it, not each pair. RES-012 reports no homogeneity test when only one arm has exposed players or when every exposed player, or none, is late, and then never escalates. None of the rules checks that a first exposure follows the assignment or falls inside the outcome window.
- RES-005, RES-006, RES-009 and RES-010 are not built. They check how someone else analysed the data; Referee computes the analysis itself, with Bonferroni, Benjamini-Hochberg or Benjamini-Yekutieli corrections and the delta method (20.5), so there is nothing for them to check.

### 21.5 The cohort test, RES-007 (4b-2)

- Cohorts. A cohort is the players of one arm whose first exposure falls in one block of 7 days, counted from `design.start_utc` when the spec registers one and from the first assignment otherwise. For each non-control arm and cohort: the Welch difference against control (absolute scale) and the log ratio of the means (relative scale; a cohort whose mean in either arm is not positive is dropped with the reason `non_positive_mean`). Each standard error is multiplied by the correction of 21.1. Q and the slope per block come from `cohort_heterogeneity`.
- Usable cohorts. A floor of 30 players per arm, never lowered. The registered size adds a preference: the minimum per arm is the larger of 30 and ⌈7·R / (4·D)⌉ (R the arm's required n by name, D the planned duration), used only if it keeps at least 90% of the cohorts that reach the floor and at least 3; otherwise the floor is used and the finding says so. The finding always reports the registered size, the achieved size, the preferred minimum and the one used. The preference is bounded because it changed no result on a plan that is on schedule: with a minimum of ¼ of the planned weekly share, applied whenever at least 3 cohorts reached it, it kept the same cohorts and gave the same results as the floor alone in 6,840 of 6,840 simulated on-plan cells, and the fall-back to the floor happens when the registered size is more than about four times what can be enrolled, a plan that DES-001 already blocks (both reported; the 90% guard is new and was not simulated). A cohort with no variation is dropped with the reason `no_variation`.
- Block length. Weekly blocks when at least 3 cohorts are usable, there is a usable cohort in each half of the weekly blocks inside the assignment window, and the median size of those blocks (empty ones counted as 0) in the smaller of the two arms is at least 60 players. Otherwise 14-day blocks, when the plan is at least 42 days, at least 3 of them are usable and there is a usable one in each half; otherwise not evaluated. The choice uses cohort sizes only, never outcomes; the finding names the block length used and never reports both lengths' results (the traffic of 21.6 prices both, from sizes alone). A coverage rule of "half the blocks" alone let a test cover only the first half of the window, and without the 60-player rule power fell from 52.4% to 41.2% as traffic rose from 8 to 10 installs a day (both reported).
- Operational readings (`referee/src/referee/cohorts.py`; judgement where marked). The window of a plan holds ⌊D / b⌋ whole blocks of b days. Its first half is the blocks numbered from 0 to below ⌊D / b⌋ / 2 and its second half the others; a block after the end of the window counts as second, and a block before the origin (a first exposure logged before the assignment, which no rule checks) as neither, so it cannot make the cohorts cover the first half. The median of the weekly rule is taken over the blocks of the window, the smaller of the arm and control in each, an empty block counting as 0. A cohort is usable when both the arm and control reach the minimum in it, each at the minimum of its own registered size. For 14-day blocks the preferred minimum is ⌈14·R / (4·D)⌉, the weekly formula scaled by the block length, and the median rule is not applied (both judgement: the formula and the 60 players were found for weekly blocks, and neither was simulated for fortnights). A cohort counts only analysed players, by the block of first exposure, so players never exposed and players exposed late are in none.
- Statistics readings (`referee/src/referee/cohort_effects.py`; judgement where marked). The absolute scale is Welch's difference of the metric's values, for a binary metric too (the 0/1 values, unpooled standard error; judgement: the pooled two-proportion test would not be the Welch error the correction of 21.1 was validated on). The relative scale is the log of the ratio of the two means, with the delta-method standard error sqrt(s₁²/(n₁·m₁²) + s₂²/(n₂·m₂²)) and Satterthwaite degrees of freedom for those two parts (judgement: 21.1 says "the Welch degrees of freedom" and was validated on the absolute scale). Each scale multiplies its standard errors by √(ν/(ν−2)) with its own ν. Q and the slope are computed over the cohorts that remain, the slope against the block numbers, so a block left out leaves a gap rather than closing it. A cohort is dropped from a scale, and listed with its block, when it has no variation in either arm (`no_variation`), when a mean is not above 0 (`non_positive_mean`, log scale only), or when the numbers cannot be handled, such as a value beyond any float (`not_estimable`). A scale left with fewer than 3 cohorts is not evaluated and carries the commonest of the reasons it dropped cohorts for, the first in the alphabet on a tie; the other scale is unaffected. A failure of Q itself is reported as `not_estimable` with its message, never raised. So is a failure of the shifts the test could have seen, or of the control's mean by cohort: the arm and metric is `not_evaluated` with the reason `not_estimable` and the message in `error`. The control's mean by cohort is taken over the cohorts that either scale kept, so a cohort that both scales dropped is not in it.
- Flag. A scale shows heterogeneity when Q or the slope has p below 0.025 divided by the number of non-control arms (Bonferroni, as `plan_power` does). RES-007 flags an arm only when both scales show it. Neither scale is invariant: with a constant relative effect and a baseline that a build or campaign moves, Q on the absolute scale flags 9.2%, 21%, 66% and 99.6% of runs at 100, 300, 1,000 and 3,000 installs a day, and on the log scale a constant absolute effect does the same (27.7% at 100 installs a day). Requiring both kept false alarms at 3.3% to 4.4% in the rows tested, at a cost in power for a fade (75.9% to 49.5% at 40 installs a day) (all reported, binary outcomes). Q-or-slope at these levels and the two scales were not measured together; 4b-2 measured them, and the result follows.
- The levels, measured (`referee/tests/cohort_simulation.py`; results in `referee/docs/simulations/`, 5,000 replications a cell, seed 20261211, Monte Carlo error 0.28 points at 4%; the simulation's statistics are checked against `referee/src/referee/cohort_effects.py` on random datasets and its flags against `trigger`). With two arms and a baseline that does not move (a null of no effect and a null of a constant relative effect of +20%; 96 cells of normal, Poisson, lognormal and binary outcomes, 3, 4, 8 and 12 cohorts, and 30, 100 and 300 players per arm and cohort) the trigger flags 3.46% of runs on average and 5.08% at most (Poisson, 8 cohorts of 100); 95 of the 96 cells are at or below 5%, and for the normal and Poisson outcomes the mean is 4.05%. With a baseline that drifts by ±30% across the cohorts, the absolute scale alone flags up to 96.0% of runs when the relative effect is constant, and the relative scale alone up to 90.4% when the absolute effect is constant; requiring both holds the trigger to 4.0% and 3.5% at most. With three arms (two variants, the levels halved) a given arm is flagged in at most 2.47% of runs and any arm in at most 4.70% (mean 2.83%). The relative scale alone flags up to 10.8% of runs for a lognormal outcome with 12 cohorts of 30, both scales together at most 4.7%. A binary outcome at 10% with 30 players a cohort is almost never flagged (0.25% on average), a loss of power and not a false alarm. So the levels stand: 0.025 per statistic divided by the number of non-control arms, Q or the slope, on both scales. Four or more arms were not simulated.
- Power, measured the same way, for a relative effect of +40% that fades linearly to 0 over 8 cohorts of 100 players, two arms: the trigger flags 100% of runs for the normal outcome, 95.8% for the Poisson, 34.6% for the lognormal and 6.1% for the binary at 10%. Q alone on both scales would flag 99.5%, 75.9%, 13.4% and 1.6%, so the slope is what buys the power; the absolute scale alone would flag 100%, 98.3%, 37.3% and 11.0%, so the second scale costs up to 3 points (5 for the binary outcome) and is what protects against a baseline that moves. These effects are not in units of the experiment's minimum detectable effect; 21.1 and 21.6 say how that sets what can be seen.
- Heavy-tailed outcomes, measured (4b-2; `python tests/cohort_simulation.py --heavy`, results in `referee/docs/simulations/cohort_trigger_heavy.json`; 5,000 replications a cell for the trigger, seed 20261211, Monte Carlo error 0.28 points at 4%; the statistics and the flags are checked against `referee/src/referee/cohort_effects.py` as above, for unequal arms too). The outcome is a revenue that most players leave at zero: 13% of the players spend a lognormal amount whose log-scale standard deviation is 1.0, 1.5 or 2.0 (the mild, middle and heavy outcome); the mean is 3.0 per player, 23.08 per paying player, in all three. A sample shows far less of a tail than the population has: one arm of 900 players of the middle outcome, over 4,000 simulated arms, has a median skewness of 12.2 (5th to 95th percentile 7.6 to 24.3), excess kurtosis of 185 (68 to 657) and 50% of the total in its top 1% (38% to 65%), while the population's skewness is 82 (12.7 for the mild outcome and 1,123 for the heavy one); and its standard deviation is a median 0.70 of the population's (5th to 95th percentile 0.40 to 1.66; a median 0.36 for the heavy outcome), because the few large values that make up most of the variance are usually not in it. The revenue of the committed export's analysed players (731 to 969 an arm, 12% to 15% of them paying; skewness 11.5 to 19.4, excess kurtosis 151 to 463, 51% to 62% in the top 1%) lies inside the 5th to 95th percentile band of a a 900-player sample of the middle and of the heavy outcome on all three measures in all three arms, near the heavy outcome's lower edge for some (the thinnest margin of any comparison is the share of the total held by the top players of one arm, 51.2% against the band's lower edge of 50.4%; the top 1% of an arm of n players is its largest ceil(n / 100) values, as in the lab's readout; the arms differ a little in size, so the comparison is rough). The mild outcome is lighter than the export: its 95th percentile of the top-1% share, 41%, is below that of every arm, and its 95th percentile of skewness, 14.3, is below the skewness of two of the three arms (19.3 and 19.4).
- False alarms with heavy tails. With equal arms (4, 8 and 12 cohorts of 30, 100, 300 and 1,000 players; no effect, +20% and the two drifting baselines of 21.5; 144 cells) the trigger flags at most 4.64%, 3.62% and 3.34% of runs for the mild, middle and heavy outcome, 3.07%, 2.56% and 2.15% on average over the 24 cells with a stable baseline, and no cell is above 5%. The relative scale alone is far off for the middle and the heavy outcome at every size tried and for the mild outcome with small cohorts, worst with the smallest (up to 28.1%, 70.1% and 90.2% of runs; for the heavy outcome with 12 cohorts and no effect 89.5% with 30 players a cohort and 25.4% with 1,000; with a stable baseline it flags 14.4% to 27.6% of runs for the mild outcome with 30 players a cohort, 6.8% to 8.4% with 300 and 4.5% to 6.5% with 1,000, and 7.0% to 11.7% for the middle outcome and 13.4% to 25.8% for the heavy one with 1,000); the absolute scale alone stays within 5% for a stable baseline (at most 4.8%, 3.8% and 3.4%) and goes beyond it only for the mild outcome with a baseline that drifts (6.7%), where it is following the drift of the absolute effect. So the relative scale cannot stand alone. The second scale protected only the mild outcome under a moving baseline, within the grid tried (one kind of drift, cohorts up to a size given below; why the relative scale is so far off was not investigated), and the absolute scale alone rises with the players a cohort in all three outcomes: with a constant relative effect and a baseline that drifts by ±30% the absolute scale alone flags at most 2.3%, 2.5% and 1.5% of runs with 30 players a cohort and 6.7%, 4.4% and 3.7% with 1,000, for the mild, middle and heavy outcome. Its apparent protection for the middle and the heavy outcome is probably that scale's lack of power at these sizes, which shrinks as cohorts grow (an inference, not simulated beyond that size), so both scales are kept. With unequal arms (the smaller arm at the floor that 21.6 raises for the split and at three times it, 43, 69, 98 and 258 players at 2, 3, 4 and 9 to 1, and the variant both the larger and the smaller arm; no effect and +20%; 4, 8 and 12 cohorts; 288 cells) the rate is higher and rises with the number of cohorts: at 9 to 1 with 12 cohorts the mean of the cells is 5.34% with the smaller arm at the floor and 5.50% at three times it; 37 cells read above 5% (5.04% to 7.28%; the standard error of a cell is 0.31 points, and 18 are above 5.6%), all with 8 or 12 cohorts, 30 of them at 9 to 1, 19 for the mild outcome, 16 for the middle one and 2 for the heavy one (at most 5.40%); the most any cell flags at 2, 3, 4 and 9 to 1 is 4.60%, 5.46%, 5.76% and 7.28% for the mild outcome, 3.34%, 4.56%, 5.12% and 7.02% for the middle one and 2.76%, 3.16%, 3.24% and 5.40% for the heavy one. The rate does not fall with larger arms on the whole (three times the floor is higher than the floor in 123 of 144 matched pairs, the same in 1 and lower in 20, and the average difference over all pairs is +0.55 points; the mild outcome at 9 to 1 falls in 10 of its 12 pairs, by 0.52 points on average over the 12, and 10 other pairs fall by at most 0.56 points), so the floor of 21.6 is the smallest size the rule allows and not the worst. A replication of the highest cell with 8 cohorts, the middle outcome with the variant at 258 players against 2,322 in control and +20%, flagged 6.14% ± 0.14 (one standard error) of 30,000 runs with seed 777, against 6.22% in the study (the replication table of the file). Only two arms were simulated, with the same sizes in every cohort of a cell, and only this family of outcomes: a tail heavier than a lognormal's, a Pareto's for example, was not tried.
- Power is what heavy tails cost the trigger: a relative effect of +40% that fades linearly to 0 over 8 cohorts of 1,000 players an arm is flagged in 28.8%, 12.4% and 6.1% of runs for the mild, middle and heavy outcome (4.6%, 2.9% and 2.6% with 100 players), against 95.8% for the Poisson outcome at 100 (21.5).
- The smallest change a quiet result could have seen (21.7), measured. A finding says that a linear fade of some size would have been flagged with probability 80%. The checks below are of that claim for the linear fade (the step it also prints was not simulated), on the absolute scale, which is the scale the figure is worked out on, with the trigger, which needs the second scale as well, beside it; for 4 and 8 cohorts of 100, 300 and 1,000 players an arm; and with an effect that multiplies the arm's mean, as an effect on revenue, a count or a rate does, so that the spread of the arm that has it grows with it. (a) A fade of exactly the size that `cohort_detectable_shift` gives from the population's standard error under no effect (known, and the same in every cohort): Q-or-slope flags 79.3% to 80.2% of runs for the normal outcome (the trigger 74.2% to 79.0%), 76.2% to 78.7% for the Poisson outcome (the trigger 68.9% to 77.0%), 66.1% to 76.7% for the lognormal outcome of 21.5 (the trigger 57.9% to 73.2%), 67.9% to 76.2% for the binary outcome at 10% (the trigger 35.9% to 66.2%) and 27.4% to 77.8% for the heavy-tailed ones (the trigger 22.9% to 69.0%). Only the normal outcome, whose spread does not depend on its mean, is calibrated: an effect that raises the mean of an arm raises its spread too, which the figure does not allow for. When the same fade is added to every player of the arm instead, so that its spread stays that of control's, Q-or-slope flags 79.8% to 85.4% for the lognormal outcome and 80.2% to 100.0% for the heavy-tailed ones (the population's standard error is larger than the one a sample shows). (b) The figure a finding really prints is worked out from the observed, corrected standard errors (`detectable_shifts`): two arms of equal size and a stable baseline, 3,000 datasets with no effect a cell, then one fresh dataset with a fade of the printed size for each, so that a rate has a Monte Carlo error of 0.9 points at 50% (`run_printed`). For the normal and the Poisson outcome the printed shift matches it (a median of 1.00 times the shift from the population's standard error, 5th to 95th percentile 0.94 to 1.06 for the two) and a fade of that size is flagged in 79.0% to 80.2% and 76.1% to 78.8% of runs (the trigger 74.5% to 78.6% and 70.4% to 77.1%). For the lognormal outcome the median printed shift is 0.92 to 0.98 of the population's (5th to 95th percentile 0.75 to 1.20) and the flag rate 63.0% to 74.8%; for the binary outcome 66.8% to 75.1% (the trigger 36.3% to 65.4%). For the heavy-tailed outcomes the printed shift is usually smaller than the population's, a median of 0.17 to 0.96 of the population's (5th to 95th percentile 0.09 to 1.23), and a fade of that size is flagged in only 6.3% to 61.2% of runs (14.5% to 48.3% for the middle outcome), the trigger in 6.0% to 53.6%; when the fade is added to every player of the arm instead, it is flagged in 67.3% to 80.0% of runs (70.8% to 77.1% for the middle outcome), the trigger in 42.9% to 67.0%. So for Q-or-slope on the absolute scale most of the shortfall is the effect on the spread, but the estimate of the standard error is not right either: the printed shift is still a median 0.17 to 0.96 of the population's even then, because a sample shows less spread than the population, which also makes the test more sensitive than the theory with a known standard error says, and the two errors roughly offset (an interpretation, not tested separately); the trigger is 13 to 37 points short of 80% even then, and the second scale costs it 13 to 32 points. (c) The label of low information that a finding gives when the printed shift exceeds the observed mean of control (the other labels need a registered minimum detectable effect or a binary metric's events, and were not simulated) fires in 77% to 100% of the runs for the heavy-tailed outcomes with 100 or 300 players a cohort, but with 1,000 in 2% and 0% for the mild outcome, 88% and 32% for the middle one and 97% and 86% for the heavy one (4 and 8 cohorts). In the runs it does not label, a fade of the printed size is flagged in 5.2% to 61.2% of runs, in the 7 cells (of 18) with at least 200 such runs (33.1% and 43.1% for the middle outcome at 1,000 players, from 363 and 2,031 runs, against 48.3% and 47.4% of all its runs).
- Decision: the bootstrap of RES-008 is not adopted in the cohort test in 4b-2. (the statement is about `methods.bootstrap_difference`, which returns a percentile interval of the difference of means and not a standard error.) On the absolute scale the bootstrap variance of a cohort's mean is the sample variance times (n minus one) over n squared, so a bootstrap standard error of the difference is the Welch standard error that the test already uses, to within a factor of the square root of (n minus one) over n in each arm, and it would change neither Q, the slope nor the printed shift of that scale. On the log-ratio scale a bootstrap standard error need not equal the delta-method one at small cohorts, and none was simulated for the cohort test. The trigger's false alarms with equal arms are held without it (above), and with unequal arms and many cohorts they exceed 5% in places, which nothing here addresses. What the study shows instead (the figures a finding prints, part (b) above) is that the sentence of 21.7, for the linear fade on the absolute scale, is accurate for the normal outcome (the trigger up to 6 points short) and, to within 4 points, for the Poisson outcome (the trigger up to 10 points short); optimistic by up to 17 points for the lognormal and 13 for the binary outcome (the trigger by up to 24 and 44); and, where the effect multiplies spend, by 19 to 74 points for the heavy-tailed outcomes. For a heavy-tailed outcome with a registered minimum detectable effect, which only the primary metric has, the label for four times it was not simulated, but the 5th percentile of the printed shift is at least 0.56 times the population mean in every cell of the three heavy-tailed outcomes, so the label for 4 times the registered effect fires in at least 95% of the runs that print a shift when that effect is below 14% of a baseline near the mean (both example specs register 5%). The figure is therefore unreliable for revenue-like metrics (metrics like the three heavy-tailed outcomes, a judgement) that have no registered effect (secondary metrics and guardrails), and at 1,000 players a cohort the control-mean label fires in 0% of the runs for the mild outcome and in about a third (32%) for the middle one with 8 cohorts. What RES-007 prints for such a metric was decided with RES-008 in 21.11.
- Number of tests. The finding prints the number of arm and metric tests run and the number of flags chance alone would give.

### 21.6 When the cohort test does not run

RES-007 is not evaluated, with a reason code and the cohort sizes, when:

- `fewer_than_3_cohorts_reach_minimum`, or `window_holds_fewer_than_3_blocks` (a plan of 20 days or less holds fewer than 3 whole weekly blocks);
- `cohorts_do_not_cover_the_window` (at least 3 cohorts are usable but none in the first half or none in the second half) or `cohorts_too_small_for_weekly_blocks` (the weekly median is below 60 and the plan is shorter than 42 days or the fortnightly attempt fails); these two codes are added in 4b-2, and the reason given is the weekly attempt's;
- `no_variation` leaves fewer than 3 cohorts;
- `unit_not_independent`: `randomization_unit` or `analysis_unit` is `session` or `cluster`, or the two are in different classes. `player` and `user` are one class; `device` is its own class and passes only when both fields say `device`. With 6 players to a cluster and a within-cluster correlation of 0.05, Q flags 9.1% of runs with 3 cohorts and 12.8% with 8 (design-effect arithmetic, reported);
- `ratio_metric_not_validated`: the metric is a ratio. The cohort test was never simulated for one;
- `allocation_too_unequal`: the floor rises with the ratio r between the arms' realised cohort sizes, to ⌈30·max(1, (r / 1.5)^1.2)⌉ (judgement, fitted to floors of about 50, 100 and 150 to 250 at 2:1, 4:1 and 9:1 that the studies found, reported); beyond 9:1 the test is not evaluated. With a binary rate of 10% at 9:1, 8 cohorts and 30 players in the small arm, the false-alarm rate is 16.5% (reported);
- `outcome_window_incomplete`: an explicit as-of time (21.8) falls before the end of some cohort's outcome window; those cohorts are excluded and listed. With a real effect of 22% of the control mean and 300 players per arm in each of 3 cohorts, a last cohort whose windows were cut 2 to 0 days short gave 10.9% to 34.5% false alarms (reported). Without an as-of time the test runs and the report says completeness was not checked.

Readings of these gates (`referee/src/referee/cohorts.py`; judgement where marked). The ratio r of `allocation_too_unequal` is the larger over the smaller of the analysed players of the arm and of control, in all (judgement: 21.6 says "realised cohort sizes" and a ratio per cohort would let the floor change from one cohort to the next). The raised floor replaces 30 for both arms of that comparison, and the preferred minimum is never below it; r of exactly 9 is not refused. The formula gives floors of 33, 43, 69, 98 and 258 at 1.6, 2, 3, 4 and 9 to 1. The gate on units looks at both fields: `player` and `user` are one class and `device` another, anything else is `unit_not_independent`. `ratio_metric_not_validated` cannot fire in 4b-2, because the export's registry holds no ratio metric (21.3); the gate is there for the day it does. An outcome window closes at the player's `window_end_utc`, else seven days after the assignment; the as-of time is the manifest's `exported_at_utc`, or the one given on the command line (4c), and a window that closes exactly at it is complete. A cohort is left out if any analysed player of the arm or of control in it has a window that closes later, and listed with the block length it belongs to; `outcome_window_incomplete` is the reason only when the same cohort sizes would have passed without that exclusion (judgement: otherwise the shortage has its own reason), and the exclusion is made before the 90% guard of the preferred minimum is judged. Without an as-of time `completeness_checked` is false.

Traffic needed (`traffic_needed` in `referee/src/referee/cohorts.py`; judgement where marked). When a plan could not run, the finding prices what would let it from the cohort sizes it observed, not from the table below. The price is the least multiple of every observed cohort of both arms at which the plan's own rules (21.5 and 21.6) pass, with weekly blocks or else with 14-day ones as the plan itself tries them, and from which they keep passing at every larger multiple (judgement: the extra players arrive in the same weeks, in the same proportions between the arms, and are exposed at the same rate). It is found by applying those rules, with the same code the plan uses, to exact fractions of the observed sizes at each multiple where some size reaches a number a rule asks of it (the floor, the preferred minimum, and 60 for the weekly median); between two such multiples nothing can change, so those are the only ones to judge. The plan is priced, not each block length: it passes when either does, and the block length named is the one the plan would use at the price (it can change at a larger multiple; each block length's own price is listed too, and the sizes named are those that reach what is wanted at exactly the price, one of them enough where they are tied). Because the preferred minimum is judged again as the cohorts grow, a plan can pass at one multiple and fail at a larger one, so the answer is the least multiple from which it passes at every larger one, and the finding also says where it first passes (judgement). A plan that passes and then fails needs at least 10 cohorts at the floor, nine of them in one half of the window, and cohorts after the end of the window count as the second half, so this is not a curiosity of long plans: a 28-day plan whose arrivals run for 14 weeks passes at 2 times, fails at 3, 4, 5 and 6 and passes from 20/3, about 6.67 (constructed in `referee/tests/test_traffic.py`, which also searches random plans for more). The price is rounded up to a hundredth. Cohorts whose outcome windows had not closed are left out of the price as exported; where any were, the price is also worked out with them counted at the sizes observed, and the finding gives the time the last of those windows closes. That second price is what exporting again would give if no player arrives in those cohorts meanwhile, which holds at the planned end and not on an interim look, where the cohorts still filling, and those not yet begun, will hold more (the finding says so, and that weeks still to come count as empty); 1.0 there means that the plan passes at the sizes observed once they are counted, so that exporting again is enough, and the finding says to export again and also gives the price without waiting. Three cases have no price (an interim look whose empty weeks are still to come is said as such, and where only exporting again helps the finding says when), and the finding says which: a window of fewer than 3 blocks; arms more than 9 to 1 apart (traffic in the same proportions keeps the ratio, so the smaller arm must grow relative to the larger); and cohorts that scaling cannot fill, because too few blocks hold players of both arms, or one half of the window holds none, or, for weekly blocks, the median week of the smaller arm over the window is empty. The figure does not promise that the test will then be evaluated: a scale can still drop its cohorts (21.5). It does not price a longer run, or growing one arm only, which can cost less.

Segment cohorts (channel, country, platform), cohorts defined by something that happens after assignment, and retention curves read from the same players are not defined for RES-007 and are refused. Running it repeatedly on accumulating data flags 11% to 13% of null experiments (reported); the text report labels an interim run as one, the memo states the time of the export and the span of the assignments as two facts instead (23.1), and the test belongs at the planned end.

How much traffic it takes (reported; exact Poisson arithmetic, flat arrivals, floor of 30, and the earlier coverage rule of half the blocks, which the rule of 21.5 changes little but which was not re-measured; total installs a day for 95% of runs to have 3 usable weekly cohorts): with 2 arms 13.0, 11.5, 10.5, 10.0 and 9.5 for plans of 21, 28, 42, 56 and 84 days; with 3 arms 19.5, 17.0, 15.5, 15.0 and 14.0; with 14-day blocks and 2 arms 6.5, 6.0 and 5.5 for 42, 56 and 84 days. Spiky arrivals need 1.5 to 3 times as much, so the finding computes the traffic needed from the observed cohort sizes, not from these figures. Being testable is not being informative: the shift a test can see is set by the experiment's own minimum detectable effect, not by traffic, at 80% power, for 4 to 12 cohorts, at about 2.4 to 2.9 times it for a step and 2.7 to 3.2 times (slope test) or 3.2 to 4.7 times (Q) for a linear fade (reported).

### 21.7 What a finding says

- It says that the effect differs between cohorts of first exposure, not why. It never says "novelty", "decay" or "stable" as a conclusion, and never "found no difference" next to a significant trend. It states what the test cannot tell apart: a change tied to the cohort's week (a launch, a promotion, a build, the acquisition mix) from one tied to each player's own time since first exposure, which the seven-day totals do not show. For `existing_users` it adds that players who see a change first can be the most active.
- A result that is not flagged states the smallest change the test could have seen with 80% probability, computed at the trigger's level for Q-or-slope on the absolute scale (the trigger needs the log-ratio scale as well, see below) and naming its shape (a linear fade or a step), in the metric's units and as a share of the control mean. Section 21.1 shows why the slope test's figure is not Q's.
- A result is labelled low information when that shift exceeds the control mean, when it exceeds 4 times the registered minimum detectable effect, or when a binary metric has fewer than 5 expected events per arm and cohort. A flagged result that is also low information says so and calls the flag a lead to re-check.
- The control arm's mean by cohort is printed with a 95% interval and a homogeneity p value; the sentence that a changing baseline can raise Q is shown only when that p is below 0.05.
- One finding per rule. RES-007 raises one warning finding when any arm and metric is flagged, not evaluated, or flagged with low information; its evidence lists every arm and metric with its status. A RES-007 that is entirely quiet raises none, but the report always prints one line, "RES-007: N tests, k flagged, m not evaluated, j low information", so that a test that did not run cannot read as a pass. When RES-013 fires for an arm, the RES-007 finding says whether the cohorts compared hold more than one of its versions: if they do, the version change falls in the same weeks and a difference between cohorts may be the change itself; if the cohorts of every test first saw a single version, the change falls outside them (a late change in a week left out as incomplete, or after the last cohort); and if no test ran for the arm, no cohorts were compared. A test is judged on the weeks of the blocks it compared (a block of 14 days is two weeks) and on the version each player first saw, so a change that falls inside a player's outcome window is not seen; control's cohorts belong to every test, so a change of control is judged against all of them.

- Readings of these numbers (`referee/src/referee/cohort_effects.py` and `methods.cohort_detectable_shift`; judgement where marked). The shift a quiet result could have seen is worked out from the standard errors the trigger used (the corrected ones) and the block numbers of the cohorts it used, for each shape: a linear fade falls in a straight line from the shift in the first cohort to 0 in the last, and a step is the shift in the cohorts before the middle of the block numbers and 0 from there. It is the smallest shift at which Q or the slope, at the trigger's level, has p below that level with probability 80%. Q is the slope's square plus an independent remainder, so this is a one-dimensional integral, done by Gauss-Legendre quadrature and checked against simulation; the standard errors are taken as known, so it describes the cohorts of this experiment and not the design. The finding gives the absolute scale's figures in the metric's units and as a share of the control mean pooled over the cohorts used (judgement: the trigger also needs the second scale: in the fade study of 21.5 it costs up to 10.5, 9.1, 5.9 and 7.2 points of power for the normal, Poisson, lognormal and binary outcome over its two-arm cells, and 0.0, 2.5, 2.7 and 4.9 at 8 cohorts of 100 players, the example there; at the 80% shift itself it costs 1.2 to 5.6 points for the normal outcome, 1.7 to 7.3 for the Poisson, 3.5 to 8.2 for the lognormal, 10.0 to 31.9 for the binary outcome at 10% and 3.5 to 10.1 for the heavy-tailed ones (8.9 to 41.0 if the shift is added to every player of the arm instead of scaling its spend), so the figure is optimistic for the trigger by that much. If the effect also raises the arm's spread, as an effect on revenue, a count or a rate does, it is optimistic for the test itself as well: a fade of the size it prints is flagged in 6.3% to 61.2% of runs when the effect scales spend and in 67.3% to 80.0% when it is added to every player, for the heavy-tailed outcomes, 21.5). "That shift" in the low-information rule is the linear fade on the absolute scale. The registered minimum detectable effect is `design.mde_relative` times the primary metric's baseline and exists for the primary metric only; the expected events of a binary metric are the fewest of players times rate in any arm and cohort used. The control baseline is each cohort's mean with a 95% t interval, and its homogeneity p value is the chi-squared test of the counts for a binary metric (the exact test where counts are small, 21.4) and Cochran's Q of the means, with the corrected standard errors, for any other; it is not worked out when the control does not vary.

- Readings of the finding (`referee/src/referee/rules/cohorts.py`; judgement where marked). Each arm and metric has a status: `flagged` (both scales show heterogeneity), `not_flagged`, or `not_evaluated`, with the reason code of 21.6 or, for a scale, the reason it dropped its cohorts for. An arm and metric is `not_evaluated` when either scale is left with fewer than 3 cohorts, and the scale is named (judgement: one scale alone never flags, so a scale that cannot be evaluated leaves the arm unable to be flagged; the numbers of the other scale stay in the evidence). When one scale shows heterogeneity and the other does not, the note of the not-flagged result says which, and why an arm needs both (judgement: otherwise a significant trend on one scale would stand next to a bare "not flagged"). The evidence holds, for each arm, the cohort plan with the arm's and control's size in every block of both attempts and, when it could not run, the traffic needed (21.6); for each arm and metric, each cohort's estimate and corrected standard error on both scales with Q (statistic, degrees of freedom, p, I-squared, the percentage of the variation between cohorts that is due to heterogeneity rather than chance, in the words of the abstract of Higgins and Thompson, which is all of it that was read), the slope, the dropped cohorts and the trigger; for a result that ran, the shifts it could have seen on both scales, the control's mean by cohort and the low-information labels; and the sentences. The number of flags chance alone would give is the number of tests that ran times 3.46%, with 5.08% as the most (judgement: the mean and maximum of the 96 two-arm cells of 21.5 with no change over time; with three arms a given arm was flagged in at most 2.47%, and the tests of one experiment are not independent, so it is a rough guide and not a count; with unequal arms the highest of the 288 cells with unequal arms is 7.28% (one study value with a standard error of 0.31 points, not a bound) in the heavy-tailed study of 21.5, which the finding does not adjust for). An interim look is one whose assignments span fewer whole days (rounded up) than `design.planned_duration_days`, and its note quotes the 11% to 13% of 21.6. The note on `population.kind` says the declaration cannot be checked when the export has no `first_seen_at_utc` column; with the column it says what the column shows and whether the declaration agrees (23.2).

### 21.10 The pooled effect of revenue-like metrics, measured (RES-008, 4b-2)

The intervals RES-008 was planned to show (the rule catalogue of this document) are Welch's and a percentile bootstrap interval for the difference of the means of an arm and control. This section records how often each of them excludes the true difference when the metric is a revenue that most players leave at zero, by the split between the arms, the size of the smaller arm, the effect, the weight of the tail and the share of players who spend, and what candidate warnings say when it does. What RES-008 prints, and when, is decided from it in 21.11; the lines of the rule catalogue about RES-008 (the seed list of section 8) stay as written, and 21.11 supersedes them for the rule as built.

In brief (the figures are in the bullets below). With equal arms and a small effect Welch's interval is conservative in the total, though with a moderate effect the misses that remain are mostly on the side where the arm looks worse than it is; with a large effect and equal arms it is above its level, again on that side. With unequal arms it is above its level from three to one on when there is no effect or when the control is the larger arm, and the larger arm then looks better than it is; with the treated arm the larger it stays near or below its level up to three to one for the middle and heavy outcome. At nine to one with no effect the fewer players spend, the worse it is, and the number of players who spend in the smaller arm followed the rate there. In the cells it was run on, the percentile bootstrap interval missed more often than Welch's and did not repair it. The kurtosis and share warnings computed from the sample did not flag the runs in which the interval missed: the runs without a warning were the worse ones; Kohavi's rule fired in every run on the middle and heavy outcome. One family of outcomes, two arms, one kind of effect: what is not shown is listed at the end.

- What was measured (4b-2; `python tests/pooled_simulation.py --out docs/simulations/pooled_effect_heavy.json`, results in `referee/docs/simulations/pooled_effect_heavy.json`; 620 cells, 20,000 replications a cell (2,000 where the smaller arm has 10,000 players or more), seed 20261212, Monte Carlo error 0.15 points at 5% (0.49 with 2,000); `--workers` spreads the cells over processes and changes no number). An arm is compared with control by the difference of their means, as RES-008 does with Welch's interval (`methods.welch_difference`); the percentile interval of `methods.bootstrap_difference` was measured as well, to decide whether to show it (it is not shown, 21.11); the intervals are two-sided 95% intervals, so a run should miss in 5% of runs. A run *misses* when its interval does not contain the true difference of the two populations' means (zero with no effect, the effect times the control's mean otherwise); the miss is *above* when the interval lies wholly above the true difference (the arm looks better than it is) and *below* when it lies wholly below. The *split* is the number of players in the larger arm divided by the number in the smaller one. For the revenue-like outcomes an effect multiplies the arm's mean through what the players who spend spend (the share of players who spend is the same in both arms), so that it also scales the arm's spread; for the lognormal outcome it multiplies every player's amount, and for the normal outcome it adds to the mean and the spread stays. An effect that lowers the arm's mean was not run, and an effect that goes through the share of players who spend (conversion) and one that adds the same amount to every player were not simulated for the revenue-like outcomes. The outcomes are the mild, middle and heavy revenue-like outcome of 21.5 and two to check the machinery: a normal outcome, for which Welch's interval is known to be nearly exact, and a lognormal one with no player at zero (the header of the file gives all five). The statistics are computed from sums of powers of the values (the moments of the dense outcomes from the values) and checked against `referee/src/referee/methods.py` and `scipy.stats.skew` in `tests/test_pooled_simulation.py`; the bootstrap is drawn by a sparse resampler, which draws only the players who spend (their number in a resample is binomial) and has the distribution of the resamples of `methods.bootstrap_difference` (compared in the tests, on the resamples and on simulated datasets) with another stream of random numbers; `tests/test_pooled_study.py` makes cheap rows of the file again and checks every figure below against it.
- The grid, in four blocks. The main block: a smaller arm of 100, 300, 1,000 and 3,000 players and a larger arm 1, 1.5, 2, 2.5, 3, 4 or 9 times as large, with no effect (the arm the larger) and with +20% (either arm the larger): 400 cells, 80 for each of the five outcomes. Besides it come the large-arm, the effect-ladder and the payer-share blocks: 84 cells with 10,000, 30,000 and 100,000 players in the smaller arm at 1, 3 and 9 to 1 (9 to 1 only up to 30,000), 40 cells with an effect of +50% and +100% (the middle and heavy outcome, 100 and 1,000 players, 1, 3 and 9 to 1, either arm the larger) and 96 cells in which 3% or 30% of the players spend (the middle and heavy outcome, 300, 1,000 and 10,000 players, 1, 3 and 9 to 1). The bootstrap is slow, so that its 10,000 resamples were drawn for the first 2,000 replications of 90 cells and for the first 1,000 of the other 9, which have more than 5,000 players in the larger arm; the 99 cells are those of the three revenue-like outcomes with 100, 300 and 1,000 players in the smaller arm, at 1, 2, 3 and 9 to 1. Two arms only, each of one size throughout a cell. With no effect only the arm the larger is run, the control the larger being its mirror image.
- Calibration. For the normal outcome Welch's interval missed in 4.7% to 5.3% of runs in each of its 80 cells, 5.00% over all of them, so the simulation and the interval are right when the outcome is normal. For the lognormal outcome, which has no player at zero and a skewness of about six, it missed in 4.5% to 7.4% of runs in the cells of the main block and 4.2% to 5.8% with 10,000 players or more in the smaller arm.
- Equal arms. With equal arms Welch's interval is conservative for the revenue-like outcomes when the effect is small: it missed in 3.5% to 5.0% of runs for the mild outcome, 2.5% to 4.8% for the middle one and 1.6% to 5.0% for the heavy one, over the 8 cells of each (no effect and +20%, 100, 300, 1,000 and 3,000 players an arm), close to or below its level in the total, but with +20% and equal arms the misses are mostly intervals wholly below the true difference, 2.5% to 4.9% of runs against 0.1% to 2.2% wholly above (each side of an interval of this level should hold 2.5%). A large effect takes that away: with +50% and +100% and 100 players an arm it missed in 7.5% and 12.5% of runs for the middle outcome and 12.7% and 21.7% for the heavy one, and with 1,000 players an arm 5.6% and 6.9% for the middle outcome and 6.6% and 10.8% for the heavy one, and 84% to 100% of those misses are intervals wholly below the true difference: the arm looks worse than it is. A plausible reason, not tested separately, is that the arm with the large effect has the larger spread, so that it dominates the standard error, and that the mean of a sample of it is more often below its population's, which the standard error, estimated from the same sample, does not allow for.
- Unequal arms. The table gives the rate for each split between the arms, for the arm the larger and for the control the larger, at the smallest and the largest size of the smaller arm; the file has the sizes between.

The number of players who spend in the smaller arm is a candidate size for RES-008 in place of the number of players; it is a finding about one family and one kind of effect, seen at this split, to be tested on the rule.
- The percentile bootstrap does not repair this: in 86 of the 99 cells with a bootstrap the percentile interval missed in more of the replications than Welch's did, in 80 of them by more than two standard errors (of the difference of the numbers of replications in which only one of the two missed), in 9 it missed in fewer, in 2 of them by more than two standard errors, and in 4 equally often; in no cell did it miss less often than Welch's by more than 0.7 points; 97.7% of the replications in which Welch's interval missed were replications in which the bootstrap's missed too; its interval was 89% to 100% of the width of Welch's. For example, for the middle outcome with 100 players an arm and no effect, on the 2,000 replications that got a bootstrap (Monte Carlo error up to 0.7 points), Welch's interval missed in 2.2% of the replications and the bootstrap's in 8.2%; for the heavy outcome in 1.8% and 10.5%; with 9,000 players against 1,000 and no effect, on 1,000 replications (Monte Carlo error up to 1.2 points), the two intervals missed in 9.2% and 9.2% of the replications for the middle outcome and 14.3% and 16.0% for the heavy one. The percentile interval is a slightly narrower interval that misses more often, on this family, and not a better one; whether the gap between the two intervals says anything about a run was not tested. Bootstrap-t and BCa intervals, which are designed for a skewed statistic, were not tried.
- Warnings computed from the sample. Two warnings of the kind the seed catalogue names were tried at several levels (excess kurtosis above 50, 100, 200, 500 or 1,000 and a top-1% share above 30%, 40%, 50%, 60% or 70% in either arm), and the rule of Kohavi, Deng, Longbotham and Xu for the skewness beyond which a sample mean is not approximately normal: |s| > 1 and n < 355 s² in some arm, s being the skewness of the sample of n players (Kohavi, Deng, Longbotham and Xu, 2014). Kohavi's rule fired in every run of every cell of the middle and the heavy outcome (338 cells, up to 300,000 players in an arm) and of the mild outcome in the main block, in at least 99.96% of the runs of the lognormal outcome's cells there, in 6.8% to 100.0% of the runs of the mild outcome's cells with 10,000 players or more in the smaller arm and 0.1% to 75.6% of the lognormal outcome's, and in at most 0.1% of the runs for the normal outcome; with 100,000 players in each arm and no effect it fired in 100% of the runs for the middle outcome, in which Welch's interval missed in 5.3%, and in 11.7% of the runs for the mild outcome, in which it missed in 5.7%. On the middle and heavy outcome the rule is therefore a statement about the metric and not about the sample, and cannot tell the cells in which Welch's interval is right from those in which it is not; where it varies, with the mild and lognormal outcomes and many players, it moves with the size of the sample. The kurtosis and share warnings depend on the size of the sample as well as on the tail: with no effect, all splits together, and 100, 300, 1,000 and 3,000 players in the smaller arm, excess kurtosis above 100 in either arm was seen in 38.0%, 85.9%, 99.5% and 100.0% of the runs of the middle outcome and a top-1% share above 50% in 53.8%, 68.3%, 81.2% and 91.8%; for the mild outcome the shares are 12.7%, 40.7%, 71.3% and 91.5% for the kurtosis and 9.0%, 3.1%, 0.2% and 0.0% for the share of the total; an arm of 100 players of whom one spends has an excess kurtosis of 95.0, the most an arm of that size can show (the tests search for more and find none). And the warnings select the wrong runs: in the 144 cells of the main block in which excess kurtosis above 100 in either arm fired in at least 200 runs and was quiet in at least 200, the runs without the warning missed more often than those with it in 141 cells, in 125 of them by more than two standard errors, and less often by more than two standard errors in 1; for a top-1% share above 50% the same four counts are 153, 148, 137 and 0; at each of the 10 levels tried the runs without the warning missed more often than those with it in 87% to 100% of the cells that had at least 200 runs with the warning and 200 without it (72 to 163 cells); required in all arms instead of either, the runs without the warning missed more often than those with it in 142 of 142 cells for the kurtosis and 140 of 140 for the share. For example, for the middle outcome with 300 players against 100 and no effect the interval missed in 7.4% of runs; excess kurtosis above 100 in either arm was seen in 43.8% of all runs, and the interval missed in 4.6% of the runs with that warning and 9.5% of the others; for a top-1% share above 50% the figures are 51.0%, 4.1% and 10.8%. A sample that lacks its biggest spenders has a low kurtosis, a low top share, a low mean and a low standard deviation, and its interval is then the one that is wrong (an interpretation, not tested separately). So the kurtosis and share warnings tried, in either arm or in all arms, did not flag the runs in which the interval missed: they pointed the other way, the runs without a warning being the worse ones, and the absence of a warning does not say that the interval is reliable. A rule keyed on the absence of a tail, or on the shape relative to what the size of the sample predicts, was not tried. What a rule knows before it looks at the shape is the split, the sizes of the arms and the number of players who spend, and the table and the counts above are indexed by those; the table depends also on the weight of the tail, the effect and the share of players who spend, which a rule does not know or can only estimate, and a trigger on the split and the sizes could be read from the table; none was tested as a rule.
- Not shown. One family of outcomes: most players at zero and the rest lognormal, with three weights of tail and three shares of players who spend; a Pareto tail, a mixture and metrics that are not revenue were not tried. Two arms (with several arms the level per statistic of 21.5 is not the one used here), one look at a fixed number of players (no sequential looks), independent players, a difference of means without covariate adjustment, CUPED, trimming or winsorising, an effect that is a multiple of the spend of the players who spend and not of their share, smaller arms than the smallest of the table and splits beyond the largest of it. The rates of the table are those of all the runs of a cell: the rate among the runs in which a kurtosis or share warning fires is lower in nearly all of the cells counted above and was not tabulated for printing, so no range of rates is supported as the rate "when the warning fires". The percentile interval is the only bootstrap tried.

### 21.11 RES-008 and the figure RES-007 prints, decided (4b-2)

This section records how RES-008 and the "could have seen" sentence of RES-007 were built, from the pooled study (21.10) and the heavy-tailed cohort study (21.5). For RES-008 it supersedes the lines of the rule catalogue about it, which stay as written in the seed list of section 8 (warning, a kurtosis or top-1% share above a threshold, a bootstrap interval beside the t-test). It also supersedes the plans in the first paragraph and the first bullet of 21.10, which were written before the decisions below (a bootstrap interval beside Welch's). What the user decided, what is judgement and what is not shown are marked. The figures below were made from the code's constants and the saved studies when it was written; no test matches them to the text, and the studies they rest on are in `docs/simulations`.

- Decided by the user (4b-2). RES-008 fires at every split between the arms, equal arms included; it shows no bootstrap interval; and the size its rates are read by is the number of players who spend (a value other than zero) in the smaller group, the smaller group being the one with fewer analysed players (of two of the same size, the one with fewer players who spend, then control). Decided earlier and still standing: the trigger is Kohavi, Deng, Longbotham and Xu's rule or the seed list's kurtosis and top-1% share; the wording states the measured rates and that they come from one simulated family; and RES-007 always prints the measured rate of its figure.
- What the rule reads. Every non-control arm against control on the analysed players (21.3), for the primary metric and each guardrail that is not binary, metric by metric in the spec's order and the arms in the spec's order inside each. A group is read on its own: with fewer than two players, every value zero, every value the same, a negative value, or values that are not finite or are too large or too small to measure, it is reported with its reason and the pair is judged on the other group. A pair with no sign and a group that could not be read is counted as not evaluated and does not fire the rule alone; a pair that shows a sign does, whatever the other group. `heavy_tail_report` gives the evidence (summary, settings, tests, notes) as `cohort_report` does, and its summary line is for the report of 4c to print (until then a quiet RES-008 prints nothing).
- The signs. In either group: (K) a sample skewness above 1 in size in a group of fewer than 355 times the square of that skewness in players, the rule of thumb of Kohavi, Deng, Longbotham and Xu (2014); (E) an excess kurtosis above 100; (T) the top 1% of the group's players holding more than 50% of the total. The skewness, kurtosis and share are rounded to 6 places, and the decision is made on the rounded figures that the evidence shows. K or E fired in every replication of every one of the 439 revenue-like cells of the pooled study (T can only add to them), so that study cannot place the levels 100 and 50%, which are judgement, and E cannot fire in a group of fewer than 105 players, since the most a group of 104 players can show is below 100. Kohavi et al. built their rule to keep the total error of a 95% interval for one mean within 4% to 6% at the size it asks for, and they say that when the two groups have the same distribution and equal sizes it gives no useful bound; the finding says so for groups within 1.25 to 1 of each other in size, with the rates the study found.
- The rates. The table `referee.pooled_rates_table` is generated from the saved study by `python tests/pooled_rates_table.py > src/referee/pooled_rates_table.py` and a test makes it again and compares: 100 cases from the 439 revenue-like cells of the study (the 40 of the ladder, +50% and +100%, included), each the lowest and the highest rate of Welch's 95% interval over the cells of its effects (`small`: none and +20%; `large`: +50% and +100%), which arm is the larger (equal, the arm or control; a cell with no effect counts for both, since the two arms are drawn alike), the split and the players who spend in the smaller arm. A comparison is placed by bracketing: the two splits of the grid that bracket it and, at each, the two numbers of players who spend that bracket its own; the range is the lowest and the highest rate of those cases, in exact arithmetic, and a comparison on the grid gets its own case. Beyond the grid the nearest edge is used, the evidence names the direction, and the range is called a floor ("the true rate is probably above this range") only where the highest rates of the table rose in that direction by more than a point. The cases on the two sides of a comparison are far apart when their players who spend differ by 5 times or their splits by 2.5 times; the finding then says so and adds the nearest case, or all the cases at the same nearest distance, beside the range, which still sets the severity, because the grid for `large` effects is sparse (two numbers of players who spend, three splits). In the simulated cases the arm is the group with the higher mean (only positive effects were run), and the sample does not say which group that is: a seeded check (13% of players spend, the arm the smaller group at 3 to 1 with +20%, 300 players in the smaller group, about 39 of them who spend; `tests/test_sign_of_the_difference.py`) found the group with the higher mean seen to be the one with the lower true mean in 40% of runs, and in 63% of the 62 runs in which Welch's interval excluded 0 (one seed: read them as large, not as exact). Groups about equal in size (up to 1.25 to 1) are placed among the cases of groups of the same size; for other groups the range is the lowest and the highest of the ranges for the arm the larger group and for control the larger group, because the sample cannot be relied on to show which group has the higher mean (the arm, in the simulated cases; with many players who spend it can, and the range is then wider than it needs to be); near 1.25 to 1 the rate can be higher than the equal cases show when the larger group is the one with the lower mean; the evidence says which with `read_as`, `equal` or `both_orders`, and the cells of a range read both ways round are counted once. The rule cannot see the true effect, so a range for each of the two sets of effects is always printed, with the number of cells, how many of the three tail weights they cover and the fewest experiments in a cell, and a note that a rate carries simulation noise.
- The difference seen. The finding prints the difference seen (the arm less control) as a share of control's mean, and when the arm's mean is lower the effect in the terms of the simulations, and Welch's interval for it, before anything else. The effects are nearer +50% and +100% from a difference seen of 35% (the higher mean over the lower one, which is how the simulations measure an effect), halfway from +20% to +50%, and nearer none and +20% below it; the range for the nearer effects is put first, and it is the one the severity reads. That level is a judgement at one point, so a difference close to it can switch which range sets the severity, and the finding says so. Which side the failed intervals fell on is said only where the study showed one: with `small` effects and groups of unequal size, most made the larger group look better than it is; with `large` effects and groups of about equal size, most understated the gap between the groups; with `large` effects and groups of unequal size the side depends on which group has the higher mean, which the sample does not show, and the finding says none.
- Where the rates are quoted. Only for `revenue_usd_7d`, money that most players leave at zero, for specs that randomise and analyse one class of independent players (`player` or `user`, or `device` for both: the test of RES-007, shared), and when the smaller group has a player who spends. Any other metric (`sessions_7d`, `purchases_7d`) gets its signs, called "skewed" when only K shows, and a statement that no error rate was measured for it, because the Welch interval of a count metric was not simulated; so does a spec whose units are not independent players. The finding says in the reader's terms which group is the larger, which side most failed intervals fell on, and that the rates are those of all the simulated runs: the runs whose sample showed a kurtosis or share sign (each compared alone) failed less often than the others in nearly every setting where both kinds of sample were common, so for a sample like the one in hand the rate may be lower, and every simulated run of a revenue-like metric showed a sign, so the range is also the rate among those that show one.
- Severity (judgement, to be confirmed). The default severity is info, with an escalation to warning when the range for the effects nearer the difference seen reaches above 7.5% (1.5 times the 5% an interval of this level should fail in) or that comparison is beyond the simulated cases in a direction in which the rates rose. When the means cannot be compared (a mean is missing, or both are zero), both ranges count. This departs from the seed list's warning: with a warning every revenue-like metric would give the verdict caution whatever its data, because every simulated run showed a sign. As built, the verdict follows the data seen: the highest rate of any case for equal groups is 5.9% with none and +20%, and at least 10.8% with +50% and +100%, so groups of about equal size with a small difference stay info and with a large one escalate; for groups of unequal size the range over both orders reaches above 7.5% at 32 of the 43 combinations of split and players who spend that the table holds for groups of unequal size, so most of them escalate (the range includes the order in which the larger group has the lower mean, where the rates were highest), as does a split beyond the grid in a direction in which the rates rose. An info finding is listed and leaves the results verdict at `clear`; a metric that is not revenue-like (count metrics) is info, since no rate was measured for it.
- A quiet RES-008 is not a pass. The report always prints the line "RES-008: N comparisons (binary metrics are not read), k with a sign of a heavy tail, m not evaluated. No sign is not a pass", and a pair with no sign, or that could not be read, gets a sentence inside a finding that fires. The simulations hold no run without a sign, so a quiet RES-008 says only that the metric is less skewed, or the sample larger, than anything simulated.
- What RES-007 prints. Its sentence about the smallest change a quiet result could have seen now says that the 80% is the power calculation's claim, which takes the standard errors as known and the spread of the arm as unchanged by the effect, and then states the share of runs in which the trigger flagged a fade of exactly the size printed (21.5), by the kind of metric, over 4 and 8 cohorts and the three sizes of 100, 300 and 1,000 players an arm in a cohort taken together: revenue-like metrics 6.0% to 53.6%, a binary metric at a rate of 10% 36.3% to 65.4%, counts simulated as Poisson 70.4% to 77.1%, and 42.9% to 67.0% for revenue-like metrics when the same amount is added to every player. A finding prints the range of the size nearest its own in logs, for example 6.0% to 22.8% for revenue-like metrics at 100 players an arm in a cohort. The step was not simulated. The rate is quoted only inside the design that was simulated: two arms of equal size (up to 1.25 to 1, a limit chosen and not simulated), 4 or 8 cohorts, 100, 300 or 1,000 players an arm in a cohort and a control baseline that does not move (the p value of the test that the control's mean is the same in every cohort is 0.05 or more, or cannot be worked out); the players an arm in a cohort are the median over the cohorts used of the smaller arm, and between the sizes and the numbers of cohorts simulated the test counts as inside (judgement). Inside, the share quoted is that of the simulated size nearest in logs, and outside the note says that the share is not known there and gives the range over the cases simulated, as indicative. Which simulated kind stands for which metric is a judgement: `revenue_usd_7d` for the revenue-like outcomes, `purchased_7d` for the binary outcome, `sessions_7d` for the Poisson outcome and `purchases_7d` for the binary outcome and the Poisson outcome; `purchases_7d` is a count that is mostly zero or one. The sentence "a little optimistic" is gone: the rates replace it.
- Judgement in the figure of RES-007. The test of whether a design is inside the one simulated is a continuous range, so a number of cohorts between 4 and 8 and a size between 100 and 1,000 players an arm count as inside although only the numbers and sizes named above were simulated; a control baseline moves when the p value of the test that its mean is the same in every cohort is below 0.05, and does not move when that p value cannot be worked out; and the binary row is a rate of 10%, quoted without comparing it with the rate of the metric. `FADE_FLAG_RATES` and `FADE_FLAG_RATES_ADDED` of `referee.cohort_effects` hold the lowest and the highest share of runs per kind and size of `docs/simulations/cohort_trigger_heavy.json` (made by `tests/cohort_simulation.py --heavy`), and `tests/test_fade_rates.py` compares them with it; when the study is run again they are copied from it and that test says which entries differ.
- Judgement and not shown. The levels of E and T; the severity and its level; the groups "about equal in size" (up to 1.25 to 1); the hull in place of an interpolation, and reading unequal groups in both orders instead of by the sign of the difference seen (the seeded check supports it, for one family only); the effects nearer the difference seen and the level at which they change; a rise of a point before a direction beyond the grid is called a floor; the far-apart limits, and the nearest case as the least sum of the absolute logs of the ratio of the splits and of the ratio of the players who spend; the mapping of metrics to simulated kinds; quoting no rate for a count metric. Disclosed and not changed (decided by the user in the final review of 4b-2): the severity follows the effects nearer the difference seen, which for a heavy-tailed metric is itself noisy, so with equal arms an experiment with no effect can read as a warning and one with a large effect as info (a seeded run of the rule on simulated experiments showed both, in a share of runs that is not part of the committed studies), and above 130 players who spend in the smaller group the range of the 130 case is used, a possible ceiling where the simulated rate fell as the number grew (for a large effect and equal arms from 7.5%-21.7% at 13 to 5.6%-10.8% at 130), so that the severity can stay a warning however many spend; a simulation of 1,000 or more players who spend, and a rule that does not choose the effects by the difference seen, would settle it. The notes of the finding and the rule text say so. Not shown: the rate among the runs in which a sign shows (it is the range, see above), a robust or capped version of the metric (Kohavi et al. report, in a paper that Referee's author read in a saved extract, that capping revenue per user cut its skewness from about 18 to about 5; Referee has not measured how well that works), a bootstrap interval (21.10 found the percentile interval no better), more than two arms, an effect that goes through the share of players who spend, and a metric with a heavier tail than the lognormal.

### 21.12 RES-004, a guardrail worse than its tolerance allows, decided (4b-2)

This section records how RES-004 was built. For this rule it supersedes the line of the rule catalogue about it, which stays as written in the seed list of section 8 (a blocker, "guardrail breached beyond tolerance in the harmful direction"). What the user decided, what is judgement and what is not done are marked. The figures below were made from the code's constants when it was written; no test matches them to the text (decided by the user in the final review of 4b-2: a test earns its place by guarding behaviour, not by matching prose).

- Decided by the user (4b-2). "Breached" is read on the 95% interval for the harm, in two strengths: a breach is shown, or it is only possible. The tolerance is measured against 2 references and the stricter decides. The note says when they disagree. A shown breach is a blocker and a possible one a warning.
- What the rule reads. Every non-control arm against control on every guardrail of the spec, in the spec's order, on the players the effect rules use (21.3): assigned, exposed, and not first exposed after their first purchase. A guardrail is a metric of the export's registry (21.3), binary or continuous. The guardrail's `baseline_std` is not used.
- Open outcome windows (judgement). A player whose seven-day outcome window closes after the time of the export (the manifest's `exported_at_utc`; a window that closes at that instant is complete) holds only part of a week of sessions, purchases or revenue, so the mean of such players falls short of a registered baseline that is a whole week's: an arm that changed nothing reads as worse, and a harmful rise can be hidden. Those players are left out of every reading of RES-004, as the cohort test leaves out their cohorts (21.6), and the evidence and a note say how many, by arm. This departs from the population of 21.3, and it is the same players for both references on purpose, so that the figures of the two rest on the same players. Without a time for the export nothing can be told and every analysed player is read. An export taken when accrual ends has the last week's windows open, so the readings rest on the earlier weeks, and an export taken again after they close reads them.
- Independent players (judgement). The intervals take the players to be independent draws, as the effect rules do (21.5), but RES-004 does not stop for a spec whose randomisation or analysis unit is a session or a cluster, or a mix: it reads the rows it is given and the evidence says `units_independent: false`, with a note that the intervals are then narrower than 95% suggests and a breach shown may be a false alarm. The size of the excess was not measured by Referee (an exploratory simulation of clusters of 20 with a correlation of 0.10 showed a nominal 5% false breach at nearly 19%), and no hold is applied: whether a shown breach should be held to possible for such a spec is left to the user.
- The harm. The change in the guardrail is turned into a share of a reference value and signed so that positive is worse: the sign of the change is kept when an increase is the harmful direction and flipped when a decrease is. The spec says a guardrail is breached when it is worse than the baseline times one plus or minus the tolerance; Referee reads that as a harm strictly above `tolerance_relative`, so a value exactly at the tolerance is not a breach (judgement). The note prints the tolerance as it was registered, without rounding and to at least one decimal, and each harm with the decimals that keep it on its own side of the tolerance.
- Two references. Against control's observed mean, the ratio of the means of the arm and of control, with an interval from the log scale (the delta method on the log of each mean, with Satterthwaite's degrees of freedom: `methods.mean_ratio`), so that the uncertainty of the control's mean is in the interval; the change is the ratio less one. Against the registered baseline, the arm's own mean with a t interval, or its rate with a Wilson interval (`methods.mean_interval`, `methods.proportion_interval`); the registered baseline is taken as a constant. Both: each interval is a two-sided 95% interval (alpha 0.05). The stricter of the two strengths decides, and the evidence names the references that decide and whether they agree.
- The strengths. A breach is shown when the whole 95% interval for the harm is beyond the tolerance, and possible when only the point estimate is. A comparison whose point estimate is within the tolerance is within it, even where the harmful end of its interval is beyond the tolerance: a point estimate within the tolerance is not a finding, and the evidence marks such a comparison as one in which the data cannot rule out a breach, which the summary line counts. The harm and its interval are rounded to 6 places, and the decision is made on the rounded figures that the evidence shows.
- Held to possible (judgement). Three kinds of reading can only make a breach possible, never shown: two because their intervals cannot carry the claim, and one because the arm may owe it nothing. First, an interval with no width: when every player of a group has the same value its standard error is zero and the harm would be called certain from any number of players, which `methods.mean_interval` refuses for that reason. It is believed only when chance cannot explain it. The chance is worked out that so many players drawn from the other group, at its share of players with that value, are all alike, and a reading is held when that chance is not below 2.5%. A few players of a revenue arm all at zero, with a few in a hundred of control's players buying, are held; thousands at zero are shown; players at a value that nobody in control has are shown at any size. The same test is made for the ratio against control's mean when one of its groups has no variation, since its interval then takes its width from the other group alone. It treats players as drawn independently from the other group's distribution, which is an assumption and not a test of the arm. Second, the registered-baseline reading of a revenue-like guardrail (most players at zero, a few large: the family of 21.10, taken from the metric's name without looking at the values) when a fall is harmful and the group has some spread: the t interval for the mean of right-skewed data lies wholly below the true mean more often than it should, and for a fall that is a false breach. `tests/test_guardrails_calibration.py` simulates this for one size and one such family. The reading alone shows a fall in a harmless arm more often than a calibrated limit would, and the rule with the hold much less often; the reading against control's mean is not held, because it was the better calibrated of the two there, although at the tolerance itself it still showed a breach somewhat more often than a calibrated limit would; a rise is not held, because the baseline reading hardly ever shows a rise that is not there in such data, so a hold would take away no false breach and could only cost power; which of the two readings shows a real rise first depends on how large the rise is and on how many players there are (the test pins a small rise, which the reading against control's mean shows more often, and a large one, which the baseline reading shows more often). The price of the hold is power, and the test pins it: at a fall of three times the tolerance a blocker is much less likely than on the baseline reading alone (the test pins by how much), and the rest of those draws are warnings. The note says when a reading was held and why. Counts (sessions, purchases) are not held; the same interval can over-show a fall when the counts are small, and Referee has not measured by how much, which the note says for a count whose fall is harmful. Third, decided by the user in the final review of 4b-2: the registered-baseline reading of an arm when control itself is shown beyond the tolerance of the registered baseline (the whole interval of control's own place) while the reading against control's mean is within the tolerance. The arm may then be what control is, and a blocker for it would be a verdict on the baseline and not on the arm. The reading is held to possible, so the finding is a warning; a reading against control's mean that is possible, shown or not measured leaves the baseline reading as it is, and so does a control that is only possibly beyond the baseline. The note says that the reading was held and why. Groups that are nearly but not exactly alike (all at zero but for one small purchase) are not held either: the chance test is for groups that are exactly alike, so they go to the ratio's interval as it stands, and a total collapse that chance explains can still read more weakly than a near-total one.
- Not measured. A reference that cannot be measured says why, naming the group, and the other decides. Against control's mean: a group with fewer than two players; neither group varying; the mean of the arm not above zero (the ratio of the means has no logarithm, so no interval can be formed, though the fall may be the whole of control's mean, which the note then says); control's mean not above zero (a share of nothing is undefined); numbers too large or too small. Against the registered baseline: a mean of fewer than two players (one player is enough for a rate); a registered baseline not above zero; a spread too small to measure; numbers too large or too small. A binary guardrail with fewer than 10 players on one side of its rate, in the arm or in control, is marked as rough. No infinity or not-a-number reaches the evidence.
- The baseline that moved. Control's own place against the registered baseline is in the evidence: when control itself is beyond the tolerance of the registered baseline, the baseline may no longer describe this traffic, and the note says so. If the baseline reading is also beyond the tolerance, it adds that a breach against the baseline alone does not show that the arm caused it, unless the reading against control's mean shows the breach too, or the arm is at zero against a control that is not and more of its players are at zero than chance explains, where the arm is plainly the difference. Where control's own reading was held, the note says so.
- A tolerance out of reach. A fall of a metric that is never negative is at most the whole of any reference value, so a tolerance of one hundred percent or more cannot be exceeded on either reference; a rate cannot rise above one, so against a registered baseline whose rate times one plus the tolerance is not below one, the reading against the baseline cannot show a breach. The note says so, the evidence lists the references concerned, and the summary line counts the comparisons for which no data could show a breach. A check of the spec for such a tolerance, which needs no data, is not part of this step.
- Severity (judgement). RES-004 is a warning, escalating to a blocker when a breach is shown in at least one comparison. This departs from the seed list's blocker: a breach that is only possible is, by the user's choice, a warning. As 21.3 words the verdict, any blocker makes the results verdict `invalid`, including this one; whether a shown breach should read differently is left to 4c. The rule fires on a possible or a shown breach only: a guardrail within the tolerance, or one that could not be measured, is counted in the summary and prints nothing, and the report of 4c prints the summary line.
- Judgement and not done. The strict reading of the tolerance; the log scale for the ratio and the Wilson interval for a rate; the stricter of two references; the limit of rough counts; the three holds; the severity. The intervals are unadjusted, one for each arm, guardrail and reference, so with several of them some will miss, and a revenue-like guardrail has the heavy-tail problem of 21.10 and 21.11: the rates RES-008 reports were measured (21.10) for Welch's interval for a difference of means and are not the rates of these intervals, and the only measurement of these is the simulation above, exploratory, for one size and one family. Not done: no sequential looks (one look, at the end; extending the test until the interval clears the tolerance is a second look that the interval does not cover, and the remediation says so); a power calculation for the guardrail's interval (its width is what decides whether a breach can be shown); an interval for the mean of a skewed metric whose rate of missing is known, which would let the hold be lifted; an exact test, in place of the chance of so many players alike, for an arm at zero against control; a margin other than the registered relative tolerance, an absolute tolerance, and a ratio metric (21.3).

### 21.13 DES-009 and the DES-003 note for new users, built (4b-2)

This section records how DES-009 and the new-users text of DES-003 (both in 21.8) were built. The figures below were made from the code's constants when it was written; no test matches them to the text (see 21.12).

- What DES-009 is. DES-009 is an info rule, a forecast from the plan alone and not a finding about data: it says that the cohort check of the results review (RES-007, 21.5) would not run on the plan even if players arrived perfectly evenly. It reads `design.planned_duration_days`, `population.daily_eligible_units`, the arms' allocations and the two units (`referee/src/referee/rules/design.py`), and is run by the design review, not the results review.
- What changed from 21.8 as first written (judgement). 21.8 first wrote one threshold, 45 players per arm and week. The figure came from the study of 21.6, which counted only the floor of 30 players; the median of the weekly blocks, the floor that rises with the ratio of the arms, the refusal of arms far apart and the fall-back to longer blocks were added to RES-007 after it, and a review of the first build showed that the single figure was wrong on each: a weekly plan at that threshold was told nothing though RES-007 cannot run on it, an unequal split was judged by the smaller arm alone, and a long plan was told that RES-007 would probably not run where its longer blocks run it. So DES-009 now applies the gates of RES-007 itself (`forecast_reason` in `referee/src/referee/cohorts.py`, which calls the functions that `plan_cohorts` calls on the sizes the plan expects), and a test pins the two to each other at both sides of each gate. That threshold is no longer a constant of the design (21.9).
- The gates, for each non-control arm against control, with the players expected in each week taken as exact: the window holds fewer than 3 whole weekly blocks (a plan of 20 days or less); the floor of 30 players an arm and block, raised once the arms differ by more than 1.5 to 1, in the arm and in control; a median of 60 players in the smaller arm on weekly blocks; and blocks of 14 days on a plan of 42 days or more, which the weekly attempt must fail as well, the reason given being the weekly attempt's; arms more than 9 to 1 apart. A separate reason, `unit_not_independent`, is given when the randomisation and analysis units are not one class of independent units: no traffic helps, and the rule says so.
- What a pass and a fail mean. A fail is a plan on which RES-007 would not run even in the best case. A pass says nothing: real arrivals are less even than the expected numbers, so a plan that only just passes a gate still fails in many runs, most of all at the median of the weekly blocks. For the same reason the price in the evidence (`daily_eligible_units_for_even_arrivals`) is the least for even arrivals and not enough: it is found by running the same gates on larger plans, and 21.6 says that spiky arrivals need more traffic than flat ones. A plan shorter than the least window is priced at that window.
- The evidence names the reasons (the codes of 21.6, with `unit_not_independent`), the weeks of the window, the arms limited and for each its reason, its ratio and the players expected in a week in it and in control, how many arms were checked, the shortest window, the price, and the units where they are the reason. The text of the rule says what a fail costs: the results review then carries a RES-007 warning that the check could not run and its verdict is `caution`.
- What it does not look at. The share of eligible units who are exposed (RES-007 counts analysed players, so the forecast is optimistic by that share), the sizes that DES-001 and RES-002 ask for, outcome windows still open when the data are exported, and the preferred minimum (with even arrivals it can only drop blocks that pass the floor, so it cannot change the answer, which the test above shows).
- The DES-003 text for new users. When `population.kind` is `new_users` the evidence of DES-003 carries `population_kind` and a note: the accrual window and the outcome window must both fit in the time available, and 3 weekly cohorts of new players need 21 days of accrual, and 4 weekly cohorts, 28 days, if the export is taken when accrual ends; the outcome window of 7 days follows each player's assignment. The note is evidence, not rule text, so it is printed only for a spec that declares new users, and the catalogue says so in the rule's `fires_when`. The count of weekly cohorts is the least RES-007 compares and one more (judgement), because the last week's outcome windows are still open when accrual ends and that cohort is left out. A declaration cannot be checked and does not lower any warning (21.8).
- Tests and counts. The design review has one rule more, and the golden outputs of the underpowered example gained one info finding; the clean spec of the tests plans three whole weeks, so that DES-009 is quiet for it. A plan of two weeks, the least DES-003 accepts, gets DES-009 alone and still proceeds.

Delivered in: 4b-1 (this amendment), 4b-2, 4c.

### 22.2 The command

- `python -m referee review-results SPEC DATA --experiment-id ID [--as-of TIME] [--format text|json|memo]`. Exit status: 0 when no blocker fired (the verdict is `clear` or `caution`; a warning never changes the status), 1 when one did (`invalid`), 2 when the spec or the data cannot be read or reviewed (an export with problems, an unknown experiment, a metric outside the registry, an `--as-of` that is not a UTC instant), 3 for a failure inside Referee. This adds to the statuses of 17.4 and 18.3.

- `--as-of` replaces the `exported_at_utc` of the manifest (21.8). The report records the time and where it came from, `command line` or `manifest`; with neither it says so and that completeness was not checked (21.6).

### 22.3 What the report holds

- One dict, with the JSON and the text made from it (18.3). Its provenance is the fingerprint of the spec, the SHA-256 of the bytes of each of the three CSV files, and the Referee version. It carries no git SHA, package versions or timestamp: they would make the same inputs give different bytes (11, 12 and 18.3 require the same bytes), and a git SHA is not recoverable from an installed package. This supersedes the provenance named in sections 5, 11 and 17.4. The registered spec hash that 11 would refuse a mismatch against is not built: no file carries one. The report prints the hash and a reader compares it.
- The population: the origin and whether it is `design.start_utc` or the first assignment, the first and last assignment, the players assigned and analysed in each arm, and the players ignored before `design.start_utc`, listed (21.8).
- Lines that a quiet rule still prints: the summary line of RES-004, RES-007 and RES-008, each taken from the rule's own report (21.7, 21.11, 21.12). The blocking rules are grouped into data validity and harm (RES-004). A shown RES-004 breach keeps the verdict `invalid`, which settles the question 21.12 left to 4c.
- The effect of the primary metric, for each arm against control, among the analysed players (21.3) whose seven-day outcome window had closed at the time of the export, which is the reading RES-004 makes (21.12). A player whose window is still open holds part of the seven days and is left out; the number left out in each arm is `left_out`. With no time for the export no window is taken to be open, and the table says that no window was checked. For each arm the JSON report holds the two means, the difference with its 95% interval and its two-sided p value, the difference relative to control's mean when that is above 0 and finite, and the p value adjusted for the number of arms. The test is Welch's for a continuous metric and, for a binary one, the pooled two-proportion z test for the p value with the unpooled (Wald) interval for the difference, whatever `design.sided` and `design.alpha` say: the table is two-sided at 95% always. The relative difference is a point estimate with no interval of its own. The adjustment is the power plan's: Bonferroni, unless the spec registers `none`; `dunnett` is planned, and here adjusted, as Bonferroni. Its multiplier is the number of arms compared with control, capped so that the adjusted p value is at most 1, and it adjusts for the arms only, not for guardrails, other metrics or repeated looks. The 95% intervals are not adjusted for the number of arms, and the sentences above the table say so (the first build did not, and an interval that excluded 0 could stand beside an adjusted p value above 0.05 with nothing to say why). An arm with no estimate carries the reason and still counts as a comparison. The text prints the difference, its interval, the relative difference and the two p values; the means are only in the JSON. No range of p values is printed (21.8).
- Reading the table. The table is labelled by what the blocking rules advise, not by the verdict, and this replaces the label that was first decided, "not to be read while the verdict is `invalid`". NOT TO BE READ appears when RES-001, RES-003 or RES-012 blocks: their remediation says to settle the cause (the counts, the minimum duration, the late exposures) before the effect is read. UNDERPOWERED appears when RES-002 blocks because arms are smaller than the registered n, names those arms with their analysed and required numbers (from the finding's evidence; the JSON gains no field), and the intervals are what to read when the effect can be read; when RES-001, RES-003 or RES-012 blocks as well, the label says not to read the intervals yet (the first build said both "not to be read" and "read the intervals" of one table); when the design cannot be sized at all there is no registered n to fall short of, and no label (the rule's own text says to correct the spec). A RES-004 breach (a harm, 21.12) gets no label: it says the primary metric alone should not decide, not that the table is unfit to read. The JSON holds `readable`, `unreadable_because` and `underpowered`. UNDERPOWERED follows RES-002, which counts the analysed players including those whose window is still open; the table reads fewer of them (22.4).
- Origin sensitivity (21.8; this replaces its wording, "whether the verdict is unchanged for origins 0 to 6 days earlier"). Without a registered start the review is run again with the origin 1 to 6 days earlier, with nobody added or left out, and the report says which rules appear or disappear (a rule that fires at another severity does both), or that the same rules fire at the same severity. With a registered start nothing is varied, and the report says so. It is always on: the extra reviews cost time (22.4), and an option to skip them would let a run claim stability it did not test.
- Text. A list of more than 1,000 rows is cut when shown and says "showing 1,000 of N; the full list is in the JSON report" (20.3). The cut is made on the finished report and changes nothing in it. The three effect rules print their sentences (`notes`); their tables are in the JSON report. A control, format, unassigned, line-separator or paragraph-separator character in anything the text prints (a title, an arm, an experiment, a player id, a file name in a message on stderr) is written as an escape such as `\x1b`, so that a spec or an export cannot steer the terminal. What a spec or an export puts into a line is kept to that line: its newline is written as `\n`, so it cannot make lines that look like Referee's own (in a wrapped paragraph a newline or a tab is folded into a space instead). The JSON keeps the text as it is and is ASCII. A list of week numbers in a rule's evidence (`failing_weeks` of RES-011, `mixed_weeks` of RES-013) is written `week 0` or `weeks 0, 1`, because a lone `failing_weeks: 0` reads as a count of none; the JSON keeps the list. The sentence that says where an effect rule's tables are in the JSON report names those it holds (RES-007 has plans, RES-004 and RES-008 have none).

### 22.4 Judgements

- Interim run (21.6). A run is interim when the export was taken before the planned end, which is the origin plus `design.planned_duration_days` plus the seven-day outcome window. Taking it exactly then is not interim. Without a time, nothing is said of it beyond the completeness line. This is a different question from the note of RES-007 on the days observed: that note counts the whole days from the first to the last assignment, this line asks whether the planned end has come. With an origin so late in the calendar that the planned end does not exist, the planned end and the interim flag are null and the text says nothing. The memo states the two as two facts and does not call either an interim run (23.1): the export line says whether the export was taken before the planned end or at or after it (and, where the planned end falls beyond the calendar, that it was taken before it), and the days line says how many days the assignments span of the days planned (or, when they ran longer than planned, "span 21 days; 14 were planned"); the report holds both numbers (`population.observed_days`, `population.planned_duration_days`). Where the span is shorter than planned, the assumptions section says that the cohort test of RES-007 is an interim look and quotes the 11% to 13% of 21.6; that sentence follows the days, as the rule's note does, and not the time of the export. The text report keeps its INTERIM RUN line for the time of the export.
- Origin sensitivity compares which rules fire and at which severity, not only the verdict: RES-007 is a warning, and appearing or disappearing would not change a verdict that other warnings already set. A registered start is not varied: players before it were left out on purpose, and an earlier origin would bring them back. It is not run either when the origin is so early in the calendar that it cannot be moved back, and the report says so. The cost is the review run six more times, and RES-007 is nearly all of a review's time: it depends on the origin and cannot be skipped. On the committed export (2,824 players) with the shipped example, on the development machine, one review took 0.66 s (RES-007 0.64 s) and the six extra reviews about 4 s; with the binary spec of the command's tests they took about 0.35 s. An independent run on a machine about twice as slow reproduced the ratio (1.3 to 1.5 s for one review, 7.7 to 8.4 s for the six) and, on a generated export of 29,746 assigned players, measured 2.4 s for one review, 16.9 s for the six and 24.7 s for the whole command. These are single measurements; the cost beyond that size is not measured.
- The table shows no "significant" flag, and it is shown whatever the verdict, labelled as 22.3 says.
- Judgement, not yet confirmed: the effect is read among the players whose window had closed, which is fewer than the analysed players (21.3) whenever the export was taken before some windows closed. The header counts the analysed players per arm. RES-002, RES-008 and the estimates of RES-012 read all of them, windows still open included; RES-001 reads every assigned player. One report can therefore hold two differences for the same arm, the table's among closed windows and a rule's among all analysed, and `left_out` says the difference in numbers. UNDERPOWERED follows RES-002's count, so a table below the registered n because of open windows carries the left-out line and the line on the time of the export (the text report calls it INTERIM RUN, the memo says whether the export was taken before the planned end) but not that label. Reading all the analysed players, as 21.3 does, would put players with a part of the seven days into a mean of a seven-day total; whether the label should follow the table's own n is open.

### 22.5 The example and its golden

- `examples/offer-page-results.yaml` is a spec that the committed lab export can be read against; neither earlier example can, because they name arms and metrics the export does not hold. Its output on the export is `tests/golden/offer-page-results.json`. The golden is compared in numbers and layout: floats to nine digits, since they may differ in the last digits between machines (the macOS job runs the test), and the sentences not at all: the titles, explanations, advice, notes and summary lines (D3 of the review of 4b-2: tests do not pin prose). The keys of every object and their order, and the length of every list outside the sentence fields, are compared. Same inputs give the same bytes on one machine; between machines the numbers are expected to agree, not the bytes, and that is untested.

## 23. Amendment 8: milestone 4c-3 decisions (2026-10-24)

4c-3 builds the decision memo and reads the first-seen column (22.1). Where it disagrees with an earlier section it wins, and it says which it replaces.

### 23.1 The memo

- `review-results --format memo` renders the report dict as a decision memo in markdown, in the analytics lab's template (section 5): a title line, then Decision, Observed facts, Assumptions and uncertainty, Data-quality qualification and Reproducibility, in that order. It is made from the report dict and from nothing else, so it cannot say what the JSON does not. Like the report it carries no timestamp, host or path (22.3): the same spec and data reviewed by the same Referee give the same bytes.
- Decision. The memo is advisory and adds no verdict of its own (judgement). It repeats what the blocking rules advise, in the words of the effect table's labels (22.3): do not read the effect when RES-001, RES-003 or RES-012 blocks; do not decide on the primary metric alone for a RES-004 breach; report the result as underpowered when RES-002 blocks for size, naming the arms that are smaller with their analysed and required numbers (when RES-001, RES-003 or RES-012 blocks as well, "RES-002 also blocks", and the result is to be reported as underpowered once the effect can be read and the arms are still smaller, without "read the intervals"), and correct the spec when it blocks for a plan that cannot be sized. For `caution` it names the warnings and says to read the effect with them in view; for `clear`, that none of the checks objected and that this does not say the effect is real. Every memo then states what is decided here (whether the rules object to reading the result as it stands) and what is not (whether to ship, stop or continue the experiment).
- Observed facts: the verdict and the blocking groups, the counts of findings, the assignment span against the days planned and the origin, a table of the players assigned and analysed in each arm and, of the analysed, those whose outcome window was still open and are left out of the effect table ("not checked" when the export has no time), with a sentence that says who is analysed (exposed, and not first exposed after the first purchase; 21.3), the time of the export and whether it was before the planned end, the always-checked lines, and the effect table with its labels, as a markdown table. Assumptions and uncertainty: the registered allocation and baselines, the two-sided 95% tests and their adjustment, the time of the export (before the planned end, at or after it, or unknown), and, when the assignments span fewer days than planned, that the cohort test of RES-007 is an interim look, the origin sensitivity, the kind of players (23.2) and what the verdict words mean. Data-quality qualification: when the effect is not to be read, one sentence first, saying that a What to do line below that tells the reader to read, compare or report the effect applies once the blocking rules are settled (judgement: the rules' remediations are static, written for a reader who may read the effect, and are printed as they are; the sentence qualifies them and rewords none); then every finding with its why, what to do, evidence (the effect rules' sentences; the other rules' values as an indented code block, lists cut at 1,000 rows as in the text) and references, then the rules that ran. Reproducibility: the spec's id, title and fingerprint, the experiment, the three file hashes, the time of the export and its source, the Referee and report versions, and the command that gives the memo again, with SPEC and DATA as placeholders because the report holds no paths (18.3).
- Text safety as in 22.3, and more, because markdown has structure the text report has not. A value from a spec or an export is written as one line and never at the start of a line (the memo's prose is not wrapped, and the two sentences that name a value first, an arm with no estimate and an ignored player, put a word before it), in one of two ways. A title, an experiment, a player, and the name of an arm in a sentence (an arm with no estimate, the arms left out of the effect table, the arms named as smaller than registered in the label and the Decision) are code spans, fenced with one more backtick than the longest run inside and padded when the value starts or ends with a backtick or has a space at both ends. The name of an arm in a table cell, and in the notes of the effect rules (sentences of the rules with the arm inside), has a backslash before each of backslash, backtick, asterisk, square brackets, angle brackets, pipe, ampersand and tilde, and before an underscore at the edge of a word: a code span would not do in a cell, where a pipe inside one still ends it, and a note is the rule's own prose. So nothing in a value can open a heading, a list, a quote, a fence, a link, an image, a tag or emphasis, or end its cell. A bare URL, a `www.` address or an e-mail address is not changed, and a renderer that links them will. Evidence is an indented code block rather than a fenced one, because a value cannot close it. Two reviews found the gaps this closes: with wrapped prose, an arm, a player or a title could land at the start of a line and make a sixth heading (the review of the first build), and the names of arms were live inline markdown in the table cells, in the sentence on who was left out and in the notes (the review of 4c-3 after the merge).
- Tests do not pin the memo's prose as a whole (22.5). They pin the five headings in their order, that the numbers, hashes and arms come from the report, the decision sentence for each verdict and blocking group, the sentences that state a fact the reader acts on by exact string and in their section (the short arms, the time of the export and the span of the assignments), and the escaping (each mark and the fence and padding of a code span by exact strings, and the name of an arm that holds a link, an image, a tag and emphasis); the command's test runs `--format memo` on the committed export.
- 22.6 asked whether the quiet RES-004 line should say how many players were left out for open outcome windows. The line is unchanged; the memo's population table gives that number per arm, next to the assigned and analysed counts.
- The reproduce command. The experiment in it is one shell word, `--experiment-id=ID`, quoted: the id comes from the export, and an id with a space, a quote, a semicolon or a `$(...)` would otherwise be several words or a command of its own when a reader pastes the line, and one that starts with a dash would be read as an option. An id with a control character is shown escaped everywhere in the report (22.3), so the command writes `ID` for it and the memo says to pass it as the export holds it. A time from the manifest is not passed with `--as-of`, which would change the source the memo names, and the memo says that the manifest in DATA gives it and that the manifest is not among the hashed files. A real shell, not `shlex`, which expands nothing, reads the command in the tests.
- Names that a report writes the same. The text and memo reports write a value from a spec or an export with `for_line`, which writes each control, format, unassigned, line-separator and paragraph-separator character as an escape and leaves a backslash as it is, so "va" followed by U+0001 and the text `va\x01` are written the same. They are two names to the spec and to the JSON report, but the text and memo reports key the players table by the written form: one arm was dropped from it, and the effect table showed two rows with one label (found by the review of the merged memo, with a lab export whose arms were renamed; an independent hunt of four reviewers, each finding reproduced by a second, then looked for every other place that a text from a spec or an export becomes a key, and found the evidence tables and the JSON case below). The same arm keys the evidence of RES-001, RES-002, RES-011, RES-012, RES-013 and DES-004, the notes of the effect rules and the arms left out of the effect table, so one table was not the only place. The JSON report has a case of its own: it is ASCII, so a character outside the basic plane (an emoji) and the two lone surrogates that a YAML escape gives for it are written as the same two escapes, and the report then held an object with two equal keys, of which a JSON parser keeps the last. The spec now refuses arms, and guardrails, whose names are written the same by the text report or by the JSON report, with one violation that names them and the written form (status 2 for both commands, before any data is read). Judgement: a name that a report writes differently from itself is still accepted when no other name collides with it, because the reports of such a spec are right; and the check is on the written form, so it does not depend on which characters `for_line` escapes. Not covered: names that look alike and differ in what is written, such as a trailing space or a letter of another alphabet (the reports keep them apart, and a reader may not); a player or an experiment id that is written like another (they are list entries and a single value, so nothing is merged or lost, and the text shows them alike); and an arm that is called control without being the control, which the sentences that name the control group as a role then read oddly.

### 23.2 The first-seen column

- The loader reads `first_seen_at_utc` from the assignments when the column is there (21.8, 22.1), as it reads `window_end_utc`: then every row of the experiment must hold a UTC instant, and one after `assigned_at_utc` is refused as a problem of that row, because a player cannot be first seen after being assigned (the same instant is allowed). Without the column nothing changes.
- The kind of players is checked against the origin: a player first seen before the origin is an existing user, and one first seen at or after it a new user; the population's kind is the kind of more than half of its players, and at exactly half it has none (the first build let a tie fall to `new_users` and then said "by the greater number" of a number that was not greater). Judgement: the origin is the one instant the review has for when the experiment began, so it is the line between the two, and no age threshold is introduced because none is known from a source. The majority rule replaces the first build's rule that any player on each side made the population `mixed`: without a registered start the origin is the first assignment, so in a product of new users the first player, first seen minutes before being assigned, falls before it, and the review found that this turned every such population into a `mixed` one that contradicted its declaration. The report's population block carries `kind_declared` and `first_seen`: the players before and from the origin, the days from first seen to assignment as minimum, median and maximum to a tenth, the kind observed by that rule, and whether the declared kind agrees (a declared `mixed` agrees with any kind that is observed; an undeclared kind, or no kind observed, leaves it null; where every player is of one kind and `mixed` is declared, `agrees` stays true and the sentence says that the column shows only that kind, which neither contradicts nor confirms a mixed population, so that "the column agrees" is not read as a confirmation). At exactly half the kind observed is null, the sentence says that each side is exactly half and that neither kind is the greater number, and for a declared kind that the column neither confirms nor contradicts it; judgement: a declared `mixed` could be said to agree with an even split, but the column then gives no kind to compare, so no declaration is called right or wrong. ### 24.5 The narrator

- `Narrator = Callable[[ModelRequest], str]`; `ModelRequest(system, user, max_tokens)` has no field for a model name; a narrator raises `NarratorError` on any failure.
- The one narrator that ships is `command_narrator(argv, timeout_s, env)`, for POSIX (without `os.killpg` it fails with reason `start`). `--llm-command` is split with `shlex` (a failure is a fixed status-2 line) and run without a shell, in a new session. The request goes to the child's standard input as JSON, `referee-narration-request/1`, written while standard output is read through `selectors` with a deadline (never to end of file), up to 32 KiB; standard input is closed after the last byte. The read ends when the direct child has exited and what is readable is drained, so a grandchild holding standard output cannot keep the command waiting; the 120 s deadline covers the wait. On every exit path (success, error, overrun, deadline, interrupt) a `finally` kills the whole process group (`os.killpg`) before the child is reaped and closes the pipes; Ctrl-C reaches Referee only, as the child has its own session. A child that never reads its input (`cat FILE` is the documented replay) or exits early cannot deadlock the command or break its pipe. The child's standard error is discarded (`subprocess.DEVNULL`). A non-zero exit, a timeout, no output, more than 32 KiB, output that is not UTF-8 or a child that cannot start gives status 4 and one fixed line on standard error with a reason from a closed list (`start`, `exit`, `timeout`, `empty`, `size`, `encoding`), no exception text and no argv.
- Not covered: the user's command may still write files or reach the network, and a new session drops the controlling terminal, which is not relied on. N7b's stubs, each with a `timeout_s` of 1 to 2 s, required to return within it plus 5 s and never asserting a lower bound: a child that forks a sleeping grandchild holding standard output; one that exits 0 with valid output while a grandchild holds it; one that writes to `/dev/tty` where it exists; one that never reads its input (the request padded past the pipe buffer); one that exits early; an interrupt (SIGINT leaves no process of the group); one per reason word.
- No default command, environment variable naming one, `--model` option or model name anywhere in Referee; the child inherits the environment, where the user's credentials are, and Referee neither reads nor prints it. `docs/narration.md` has a six-line contract (standard input, standard output, what is discarded, the limits) and a `cat FILE` replay, and no wrapper. Referee builds no provider-SDK adapter.

### 24.6 What the narrator returns

- One bare JSON object of schema `referee-narration-output/1`, with no text field: `{"schema": ..., "findings": [{"id": "RES-001", "facts": ["RES-001.p_value", ...], "sentences": ["RES-001.why.1", ...]}]}`. Every value is an identifier the sheet holds: no number, free text, refusal channel or report-level claim. Caps (judgement): 64 fact and 16 sentence IDs per entry, 64 characters per identifier, depth 4, 32 KiB. The output's order is not used (24.7).
- The parser sees only a decoded `str` (bytes, size and process faults are `command_narrator`'s, status 4). It is strict: the standard `json` module with `parse_int`, `parse_float` and `parse_constant` refusing every number, `NaN` and infinity, and an `object_pairs_hook` refusing a duplicate key; the shape check runs before any membership test, so an unhashable value cannot raise. Trailing whitespace is accepted; other trailing text or a code fence is a violation. A 5,000-digit integer, `1e999`, a lone surrogate, an unhashable ID, a 20,000-bracket depth bomb, an over-length identifier and a `str` over 32 KiB are `schema` violations, never exceptions (N7a's corruption operators). A violation is `(code, finding ID)`, the ID shown only if the report holds it and `-` otherwise; no string of the output is echoed.

| Code | Rejects |
| --- | --- |
| `schema` | anything but one object of that shape: an extra, missing, duplicate or mistyped key, a wrong schema string, any number, trailing text, a cap exceeded |
| `scope` | an entry for a rule that is not a finding of the report, or, for an explanation, any finding but the target |
| `duplicate` | the same finding, fact or sentence ID twice |
| `fact` | a fact ID that is not in the sheet, belongs to another finding or is not offered by the intent |
| `source` | a sentence ID that is not in the sheet, belongs to another finding or is not offered by the intent |
| `coverage` | no entry for a blocker or warning (summary, next steps); an entry that selects no sentence of the kind the intent offers (an explanation needs a reason and a piece of advice); no entry at all, so only info findings may be left out, and an info target needs its entry |

### 24.8 The router, the taxonomy and the refusals

- Mechanism (judgement). `route(question)` is a pure function. It normalises as NFKC(casefold(NFKC(x))) and collapses whitespace, exactly U+0020, tab, line feed, carriage return and categories Zs, Zl and Zp (so a pasted newline is a space; every other control character is category C). A question is `unreadable` if it is then empty, over 500 characters (after normalising: tests use U+FDFA and U+00DF), without a letter, holds a character of category C (control, format, surrogate, private use, unassigned) or M (a mark), holds a letter that shows nothing (the Hangul fillers U+115F and U+1160, to which U+3164 and U+FFA0 normalise, and the braille blank U+2800), or holds a word mixing Latin with Cyrillic, Greek, Armenian, Coptic or Cherokee letters (U+0027, U+2019 and U+02BC do not end a word for that test); so a zero-width space, soft hyphen, bidirectional override, stray combining mark or Cyrillic U+0456 inside `ship` cannot split a trigger word, and a test requires `unreadable` for each, not an answer. That refusal names its reason (empty, too long, no letter, invisible or mark character, mixed scripts) and quotes none of the question. A pattern is a short sequence of token alternatives with a bounded gap, matched by a linear scan with no regular-expression backtracking; the table is data in `router.py`, its hash pinned in `router_freeze.json` (24.10), which guards the freeze and not behaviour, so pin tests are deselected when table mutants are recorded (the mutation evidence of each step). Words are matched on the text with the s of a possessive dropped (`RES-001's` is the rule `RES-001`) and with diacritics folded (a letter that NFKC composed from a letter and a mark is matched as the plain letter); readability is decided before, as above. Precedence: `injection`, then the other refusal categories in the order below, then the intents, then `out_of_scope`; a refusal category beats an intent, and an intent is answered only for a question that names a rule or holds a word of the report (a closed list: "Do you think it will rain tomorrow?" is `out_of_scope`). A clause that only says what must hold, what the review did, or why a rule says so, or that asks about "anything", is not refused for the soft words in it (ship, call, stop, trust, safe, real, enough, wait, worry and the like); `injection` is never hushed. The patterns for a finding's numbers (p value, interval, estimate, and the effect's numbers, a forecast or another test) apply where no rule is named, or, for the last five, where the question also holds a word of the effect. A target is a rule ID in the question (validated against the nine results rules, printed canonically) or a phrase from a closed table (SRM: RES-001; and so on). "Why does RES-001 block?" is an explanation, not `causal`, which matches why, because and due to only for an effect, difference or change with no rule named.
- A compound refusal prints the fixed paragraph and pointers of every category matched, in precedence order, at most three (any beyond are named), and says an answerable part was not answered. A test asserts that for each category printed its quoted sentence IDs appear.

### 24.9 The command and its exit statuses

`python -m referee narrate REPORT [--question TEXT] [--llm-command CMD] [--show-request]`

- Without `--question TEXT` the question is the summary. `--llm-command CMD` (N7b) enables path 3; without it no process is started. `--show-request` (N7b) prints the exact request the command would receive and sends and starts nothing; when no request would be made (the question is refused or `checked`, the target is quiet or unknown, the report has no finding, or no `--llm-command` is given) it prints the fixed line `no request would be made for this question` and exits 0. Not built: `--model`, `--timeout`, `--format`, `--save-raw`, any default command.
- Exit statuses, added to those of 17.4, 18.3 and 22.2, by layer. 0: a page was printed, an answer or a refusal, whatever the verdict, and the output of `--show-request`. 1: the narration was withheld because the output of `--llm-command` failed a check (the page is on standard output); it does not mean a blocker. 2: the report cannot be read, parsed or checked (24.4; problems on standard error, at most 1,000, with the exact number), or the arguments are unusable (a `shlex` failure included). 3: any exception while making the page or the sheet (a failed heading extraction and the egress assertion included); the handler prints the exception's type only, not the traceback that `main` prints for other commands. 4: the narrator failed inside `command_narrator` (24.5); one fixed line on standard error, nothing on standard output.
- Exit 0 does not mean the experiment is valid or approved, and a refusal exits 0 on an `invalid` report where `review-results` exits 1. Judgement: `narrate` is not a gate; every page says so, and `docs/narration.md` warns against `referee narrate ... && ship`. (read) `cli.main` sends every command but `review-results` to `_review_design`, so a new subcommand without its own branch would run as a design review and end in status 3 with a traceback; N6 gives `narrate` a branch of its own, and a test pins that it does not fall through.

### 24.13 Known gaps, and what is not verified

- Known gaps, as they are. The page defeats omission, not emphasis: a discounting or reassuring sentence can be selected alone and sit under the first label with the rest under the second (RES-007.do.4 alone, an info finding narrated with one discounting sentence), and a fact can be cherry-picked ("comparisons within tolerance: 1" led, "possible breach: 1" demoted). A blocker's sentence, even "Do not read the effect.", can be demoted. One info finding left out shows only its ID, severity and title. Sentences from different findings sit side by side and can be read as one claim. Lists of rows and weeks are counted, not shown. A forged but self-consistent report passes the check, and a printed report string (an arm's name) is text someone chose. The router is not injection-proof and the twelve categories are not complete. A refusal word spelt with look-alike letters of one script (an all-Cyrillic word, a dotless i) is read as another word and missed, so an intent word in the same question can get it answered; a question in a script that needs combining marks is refused as unreadable; unassigned characters follow the Unicode tables of the Python in use. A refusal word split by punctuation or a space (`sh-ip`), misspelt, or spelt with look-alikes of a script other than the five of 24.8 is missed. A clause that only says what must hold or what the review did is not refused for a soft word, so a ship request written as such a clause can be answered ("Is there anything in the review that shows we can ship it?"). A rule named switches off the patterns for a finding's numbers unless the question holds a word of the effect, so "How big is the difference between arms, given RES-001?" is an explanation. A general question that holds a word of the report ("What went wrong at Chernobyl?") is answered with the report's summary, and a terse question with none ("Give me a summary.") is refused by default (the command without `--question` prints the summary). A word of quality that opens a clause is read as an interjection, so "Valid? What did the review find?" is answered, and a statement of four or more words before a word of quality ("The sample size is fine. Confirm.") is not read as a request for agreement. The router's recall on unseen phrasing is below its fit figures, most on steering and reassurance wordings: a question answered when it should be refused gets the fixed page, which prints every finding. A valid selection can be irrelevant.

RES-004's `shown` and `possible` tiers both give `attention`, with the interval of the harm and the number of players, because an unadjusted 95% interval read at several looks raises a false blocker in 0.5% (sessions-like), 8% (binary) and 15% (revenue-like) of A/A runs over 7 looks (section 25). - The ledger. This is the registry as it is; making metrics spec-driven is milestone 6m and only shrinks the list of reasons.
- The primary metric. The difference of each arm against control with its 95% interval and the number of players, labelled as an interim reading of a design that is read once, at its planned end; no p value and no adjusted p value are printed. When the stopping rule is `sequential` the label says that Referee cannot check repeated looks. The players are those whose seven-day window had closed, as in 22.3, so the reading is of the early arrivals only: at 10 days of the lab's experiment it rests on the players assigned in the first 3 days (141 against 115 in the example), who are also where a novelty effect sits.
- Measured (101 seeds of the lab's experiment cut at 2, 3, 5, 7, 10, 14 and 21 days, planted and A/A as in section 25; the monitor, not a review): no run is `invalid` or refused for RES-002 or RES-003. Planted data is `stop_for_cause` first at day 10 in 3 seeds, 14 in 30 and 21 in 68, the first RES-001 blocker of section 25; A/A data in 2 of 101 over the 7 looks (RES-001 at days 3 and 5), inside the 0.7 expected from alpha 0.001. Not verified: real data, other generators, whether analysts find `attention` informative when it is on in every run of this data.


## 28. Amendment 13: metrics named by the spec (2026-10-29)

Replaces the closed registry of 21.3 and the name-keyed families of 21.10, 21.12 and 21.5 for the metrics a spec can declare; the registry's four metrics stay as defaults. Where it disagrees with 21.3, it wins. The data contract is `docs/data-contract.md`, generated from the loader (`python -m referee.data_contract`, a test fails if it differs).

- The spec. `primary_metric` and each guardrail take an optional `column` (the column of the outcomes file that holds the metric; default the metric's name) and `family` (`revenue_like`, `count`, `binary` or `other`). Every other column of the file is kept as a number for each player if every row holds a finite number, and otherwise listed as not numeric. Judgement: a column is a candidate metric by its content, not by a list.
- Reading a metric (`results.resolve_metrics`). A binary metric needs 0 or 1 in every row, a continuous one a finite number. A metric that cannot be read gets a reason: `column_missing`, `column_not_numeric`, `values_not_binary`, `kind_mismatch` (a built-in column declared with another kind), `kind_unsupported` (`ratio`: the delta method is still not built, and no ratio metric can be read). A results review still refuses on any of them, as it did for a metric outside the registry; the refusal names the reason and, for a missing column, the numeric columns the file does hold and the four built-in metrics.
- Family. The cohort test's table of simulated fade rates (RES-007, 21.5) is still keyed by name and so says "not simulated" for every other metric; a family-keyed table is not built.
- The monitor (section 27). Its ledger takes its roles from the spec (`primary`, `guardrail`, `other`) and prints each metric's column and family; the secondary metrics get an effect block like the primary metric's, with no p value. The reasons of 27 narrow to the ones above plus `window_not_matured` and `no_estimate`. 27 left an unreadable primary metric as a refusal and it stays one: with no primary metric there is no effect table, no RES-013 and no RES-012 estimate to build; what changed is that it is now refused only when its column is not in the export or not readable, not for being outside a list of four.

## 29. Amendment 14: the covariate adjustment (CUPED) (2026-10-30)

DES-008 has asked since milestone 2 for a pre-period covariate and nothing used it. This amendment makes the results review use it. It starts with the theory (29.1), so that what the code does can be read against it; the decisions, the evidence and the limits follow (29.2 onwards, written with the code).

### 29.1 The theory, in plain words (a note for the reader who has not met it)

- The idea. The outcome `Y` (revenue or sessions in the 7 days) differs between players for a reason that has nothing to do with the test: some players are heavy players. If the same player was measured before the experiment (`X`, sessions in the 7 days before assignment), `X` tells us part of that. Take away the part of `Y` that `X` predicts: `Y_adj = Y - theta * (X - mean of X)`. Randomisation makes the two groups alike in `X` on average, and `X` cannot be changed by a test that had not started, so the expected difference between the groups in `Y_adj` is the same treatment effect as in `Y`, with less noise. This is CUPED, Deng, Xu, Kohavi and Walker (WSDM 2013); the same estimator is a regression of `Y` on the arm and `X`.
- The best `theta`. The slope of the straight line that predicts `Y` from `X`, `theta = cov(Y, X) / var(X)`. It is the choice that leaves `Y_adj` with the least variance, and then `var(Y_adj) = var(Y) - cov(Y, X)^2 / var(X) = var(Y) * (1 - rho^2)`, with `rho` the correlation of `Y` and `X`.
- A worked example. `sd(Y) = 10`, so `var(Y) = 100`. If `rho = 0.7` the variance becomes 100 x 0.51 = 51: the standard error falls by a factor of 0.71 (from 0.45 to 0.32 with 1,000 players an arm), which is the precision of an unadjusted test with 51% of the players. If `rho = 0.3` it becomes 91, a gain of 9%. If `rho = 0` it does not change, and estimating `theta` costs a little. For one comparison: the groups differ by 1.20 in `Y` and, by chance, by 0.40 in `X`, with `theta = 0.8`: the adjusted difference is 1.20 - 0.8 x 0.40 = 0.88. The 0.32 removed is what the groups' accidental difference in `X` explains.
- One `theta` for both arms, from the data of both. It is the slope within the arms (each arm's own mean of `X` and of `Y` removed, then pooled), not one for each arm, and not the slope of the pooled raw data: that mixes the treatment's effect on `Y` into `theta`. The covariate is centred: adding a constant to `X` changes nothing (a test shows it).
- `theta` is estimated, and that costs something. An interval that treats the estimated `theta` as known is a little too narrow. The regression interval, which is what Referee computes (an ordinary regression on the arm and `X`, with a heteroskedasticity-robust standard error, HC2, and the t distribution on n - 3 degrees of freedom), includes it. The extra width is of the order of 1 / n and cannot be seen at thousands of players. In finite samples the adjusted estimate is slightly biased (also of the order of 1 / n, a result I recall from the literature on regression adjustment of randomised experiments and have not checked here); the simulations below look for it.
- What goes wrong when `X` is measured after the treatment can act. Then the treatment moves `X`, the groups differ in `X` because of the treatment, and subtracting `theta` x (that difference) takes away part of the real effect. Example: the true effect is 1.0, the treatment raises `X` by 0.5, `theta = 0.8`: the adjusted effect is 1.0 - 0.4 = 0.6, and no amount of data repairs it. Referee compares the mean of `X` across the arms and flags a difference that chance does not explain, which catches a large such effect and misses a small one. That `X` is measured before the exposure is the analyst's responsibility, written in the spec; it is not something the data can prove.
- Where it does not help. The adjustment removes only what `X` predicts. In the lab's data the pre-period sessions predict the sessions well (`rho` 0.58) and the pre-period revenue does not predict revenue at all (`rho` -0.01), because revenue is mostly the heavy-tailed amount of a few purchases. Declaring `revenue_usd_pre_7d` for the revenue metric changes nothing, and the report says so by printing `rho` and the variance ratio.
- Reading. The 1 - rho^2 formula is the standard result of the derivation above; I could not find it stated in the searched sources and it is checked here by simulation (29.4), not by citation. The Bing figure of about 50% variance reduction is the paper's own and says nothing about this data.

### 29.2 What was decided

- Where it applies. `design.pre_period_covariate` names a column of the outcomes file (data contract: `docs/data-contract.md`). When the spec names one and the column can be read, the effect table of the primary metric gets, for each arm, an `adjusted` estimate beside the unadjusted one, and the effect carries a `covariate` block. The covariate adjusts the primary metric only: not the guardrails, the secondary metrics, the cohort test (RES-007), the heavy-tail reading (RES-008), RES-004 or the estimates of RES-012, which stay unadjusted, so every finding and the verdict are the same with and without a covariate (a test compares them). The power plan does not use the covariate's correlation either (the spec has no field for it), so a registered sample size is not reduced by the adjustment.
- The registered analysis. A spec that names a covariate registered the adjusted analysis before the data; the report says so, shows the unadjusted estimate beside it as the reference, and does not pick whichever is narrower. Both carry their p values and the same adjustment for the number of arms; the verdict reads neither.
- The statistic. `methods.cuped_difference`: the arm's coefficient in the regression of the outcome on a constant, the arm and the centred covariate, with one slope for the two arms compared, the HC2 robust standard error and the t distribution on n - 3 degrees of freedom. It equals the formula of 29.1 with the within-arm slope (tested), and the estimate and the standard error equal those of a regression package (tested against statsmodels).
- A covariate that cannot be used. The column must hold a finite number for every player, must not be an outcome column (`sessions_7d`, `purchases_7d`, `revenue_usd_7d`, `purchased_7d`) and must not be the primary metric's own column. Otherwise the effect says `applied: false` with a reason (`column_missing`, `column_not_numeric`, `is_an_outcome`, `is_the_metric_itself`) and the unadjusted estimate stands. It never refuses a review: the covariate refines an estimate, and a review that is refused for it would lose the estimate it could always give. A description in place of a column name ("the primary metric measured before exposure") is `column_missing`; the design example spec's illustrative name is one.
- The balance check. The mean of the covariate in each arm against control is compared (Welch), and an arm is flagged when p is below 0.001 divided by the number of arms compared with control. A flagged arm's adjusted estimate is marked NOT TO BE READ in the text and the memo. This catches a covariate that the treatment moved by a lot and not by a little (29.4); that the covariate was measured before the exposure remains the analyst's statement.
- What the report says. The text and memo print a second table (adjusted estimate, interval, relative, p values, slope, correlation and variance left) and a sentence on what was done; a covariate that predicts nothing is shown as doing nothing (variance left 100%). For a revenue-like metric the report says that the simulated error rates of RES-008 were measured for the unadjusted interval and do not carry over to the adjusted one. The monitor shows the adjusted interval and no p value. A report without a covariate has none of the new keys: the goldens differ only in the hash of the outcomes file, which gained two columns.
- The lab export. `sessions_pre_7d` and `revenue_usd_pre_7d` are drawn from the generator's own latent engagement (the same baselines and amounts, none of the planted effects), after every older random number, so every older column of the committed export is unchanged. They are the lab's fixture for a covariate; their correlation with the outcomes follows from the generator's assumption that engagement persists, and is not evidence about real players. On the committed export: `sessions_pre_7d` and `sessions_7d` 0.58, and the review leaves 67% and 69% of the variance of the effect on sessions in the two variants (theory 1 - 0.58^2 = 67%); `revenue_usd_pre_7d` and `revenue_usd_7d` -0.01, so the adjustment of the revenue effect leaves 100%. The lab's earlier 28-day session count remains useless as a covariate (its correlation with the outcomes is below 0.03).

### 29.4 Evidence

`tests/cuped_simulation.py`, results in `docs/simulations/cuped.json` (4,000 replications a cell, 1,500 for the heavy-tailed cells; about 80 s; a study test makes a cell again exactly). Normal data, a true difference of 0.5 standard deviations:

| rho | players an arm | variance left (adjusted / unadjusted) | theory 1 - rho^2 | coverage of the 95% interval, adjusted / unadjusted |
| --- | --- | --- | --- | --- |
| 0.0 | 50 / 200 / 1,000 | 1.011 / 1.001 / 0.999 | 1.00 | 94.7 / 94.6 / 95.7 % and 94.8 / 94.7 / 95.7 % |
| 0.3 | 50 / 200 / 1,000 | 0.913 / 0.903 / 0.905 | 0.91 | 94.8 / 94.7 / 95.5 % and 94.6 / 94.6 / 95.3 % |
| 0.7 | 50 / 200 / 1,000 | 0.496 / 0.509 / 0.510 | 0.51 | 94.7 / 94.4 / 95.0 % and 94.2 / 94.6 / 94.8 % |

The variance left matches 1 - rho^2 to within the Monte Carlo error (about 0.02 at these replications), the adjusted interval holds the truth about 95% of the time at every size (the Monte Carlo error of a rate is 0.35 points), and the bias is at most 0.004 at 50 players an arm. When the covariate is moved by the treatment (rho 0.7, 1,000 an arm, shift in standard deviations of the covariate):

| shift | adjusted estimate (true 0.50) | theory | coverage, adjusted / unadjusted | balance check flags |
| --- | --- | --- | --- | --- |
| 0.00 | 0.499 | 0.500 | 95.4 / 95.6 % | 0.1 % |
| 0.10 | 0.430 | 0.430 | 40.8 / 95.5 % | 9.8 % |
| 0.25 | 0.325 | 0.325 | 0.0 / 95.0 % | 98.5 % |
| 0.50 | 0.150 | 0.150 | 0.0 / 95.7 % | 100 % |

A covariate that is moved by a tenth of its standard deviation takes 14% of the effect away and leaves an interval that holds the truth 41% of the time, and the balance check notices it in one run in ten. A covariate has to be measured before the exposure; the check is a net for the large mistake only. Heavy-tailed revenue from the lab's own model (two arms, no true difference, so coverage is 1 - false-positive rate):

| players an arm | spending scale persists | variance left | coverage, adjusted / Welch |
| --- | --- | --- | --- |
| 200 | no (rho about 0) | 0.998 | 96.4 / 96.3 % |
| 940 | no | 0.995 | 95.9 / 95.9 % |
| 200 | yes (sigma 1.5) | 0.954 | 97.9 / 98.2 % |
| 940 | yes | 0.992 | 97.3 / 97.3 % |

In these cells the adjusted interval held the truth as often as Welch's and gained next to nothing: the pre-period revenue says almost nothing about the next week's. Nothing here says that it holds for every heavy-tailed metric, a stronger tail or a covariate with a high correlation; RES-008's rates remain the unadjusted interval's.

### 29.5 Not built, and not verified

Not built: the covariate in the power plan (a smaller registered n for a known correlation); several covariates; the adjustment of guardrails and secondary metrics; an interaction term of arm and covariate (Lin's estimator, which I recall as the usual guard against an adjustment that harms; not checked here); the cohort test and RES-008 on adjusted values.
